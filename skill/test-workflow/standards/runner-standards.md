# 验收执行器规范

通用执行器（`assets/runner/runner.py`）与生成用例的执行必须遵循。核心：**真实、可定位、可复现**。

## 1. 真实验证

- **必须发真实 HTTP 请求**（真的 TCP 连接 / 端口 / 序列化），禁止进程内 mock
- 断言基于**真实响应**：HTTP status + 响应体关键字段
- 断言失败 = 用例失败，**禁止**"脚本跑完即视为通过"

## 2. 失败分类（报告必须分类，便于 AI 定位修复）

| 分类 | 含义 | 处理 |
|---|---|---|
| `STARTUP_FAILED` | 应用未启动 / 编译失败 | 先修构建与配置，不重试用例 |
| `ENV_ERROR` | 连不上 DB / MQ / 依赖服务 | **不是代码问题**，报告显式标注 |
| `AUTH_ERROR` | 401 / 403（token 缺失或无效） | 环境/鉴权问题，非业务缺陷 |
| `STATUS_MISMATCH` | 返回 status 与期望不符 | 业务缺陷 |
| `FIELD_MISMATCH` | 关键字段值与期望不符 | 业务缺陷 |
| `DB_ASSERT_FAILED` | 事务/幂等断言失败（查库结果不符）| 业务缺陷 |
| `CONCURRENCY_VIOLATION` | 并发不变式被破坏 | 业务缺陷 |
| `TIMEOUT` | 请求超时 | 排查性能/死锁 |

> **必须区分"环境问题"与"代码问题"**，否则会误导 AI 去改本来正确的代码。

## 3. 日志关联

- 每个请求必须能**关联到服务端日志**：
  - 优先：请求头带 `traceId`（或复用项目已有链路 ID），服务端日志按 traceId 过滤
  - 兜底：按**时间窗 + 请求 path** 从应用日志文件抓取
- 报告失败项必须附**服务端日志摘录**（至少异常堆栈 / ERROR 行）
- 应用日志位置与格式从项目配置读取，不写死

## 4. 数据隔离与清理

- 前置数据（`preconditions`）按用例声明准备
- 写操作（POST/PUT/DELETE）：
  - 优先运行在**专用环境 / 可丢弃数据库**
  - 或运行后按用例声明的清理方式**复位**（保证可复现）
- 禁止在共享/生产环境执行破坏性用例

## 5. 并发用例

- 用并发客户端（如 asyncio / 线程池）**同时**发出 N 个请求
- 断言**不变式**（库存 ≥ 0、成功数 ≤ 库存、无重复落库），**禁止**断言精确计数 / 精确顺序（易 flaky）
- 并发用例可重复运行验证稳定性

## 6. 可复现

- 环境参数（baseUrl / token / DB / 日志路径）**全部走环境变量或配置文件**
- 报告记录：执行时间、环境、用例数、通过/失败、失败分类、日志摘录
- 禁止 `sleep` 等不确定等待（用轮询/超时）

## 自检清单

- [ ] 发的是真实 HTTP（无 mock / 无进程内调用）
- [ ] 断言基于真实响应，脚本跑完 ≠ 通过
- [ ] 失败已分类（环境问题 vs 代码问题分开）
- [ ] 失败项附服务端日志摘录（traceId 或时间窗+path）
- [ ] 写操作有清理/专用环境，环境可复现
- [ ] 并发用例只断不变式，不断精确计数
- [ ] 环境参数走变量/配置，无硬编码
