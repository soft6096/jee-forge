# Test Workflow（验收测试工具生成）

为**已生成**的代码按需生成一套"验收测试工具"——真实调用入口，用实测结果 + 服务端日志产出报告。**默认不生成、不执行**，把"何时验证"的决定权交给开发者。

> 定位：这是主流程（ai-dev-workflow）之外的**按需补充能力**。主流程默认不写测试；需要行为验证时，开发者显式调用本技能生成工具。

## 触发与不触发

| | 说明 |
|---|---|
| ✅ 触发 | 用户显式要求：生成验收测试 / 生成接口测试 / 生成测试工具 / 生成验收脚本 / 接口验收测试 / 真实调用接口验证 |
| ❌ 不触发 | "写测试 / 写单测 / 契约测试 / 覆盖率 / Mockito / JUnit"——默认流程不写测试代码，这些说法不归本技能 |

## 输入

- 待验证的功能项 / 模块
- `docs/<模块目录>/3.<n>.2-<功能名>-接口清单（前后端通用）.md`（URL / 方法 / JSON 入参出参）
- `docs/<模块目录>/3.<n>.1-<功能名>-技术方案.md` 的**验收场景**（合法 / 非法 / 边界）
- 运行环境：base URL、鉴权方式、（事务断言时需要）数据库连接

## 产出（独立文件，不占主流程产物编号）

1. **通用执行器**：`assets/runner/` 复制到项目（一次）
2. **验收用例**：`<模块>/tests/<功能项>.cases.yaml`（从接口清单 + 验收场景推导）
3. **验收测试报告**：`验收测试报告-<模块>-<时间戳>.md`（真实请求/响应 + 服务端日志 + 结论）

## 命令

`/gen-test`（见 `commands/gen-test.md`）——只生成工具与用例，**不自动执行**；执行由开发者运行生成的脚本。

## 设计准则

- `standards/case-design.md`：用例设计——从验收场景三态推导、核心业务场景优先、**不做字段取值穷举**
- `standards/runner-standards.md`：执行器规范——真实 HTTP、失败分类、日志关联、数据隔离

## 覆盖边界（报告必须如实标注）

| 入口 | 覆盖 |
|---|---|
| Controller（HTTP） | ✅ 真实请求 + 断言 |
| Listener（MQ） | ⚠️ 可生成，需投递手段（真实 MQ 或测试注入） |
| Job（定时） | ⚠️ 可生成，需手动触发入口 |
| 无入口（框架回调 / 启动期 / 纯工具） | ❌ **不覆盖**，报告标"未覆盖" |

## 与其他 skill 的关系

- **ai-dev-workflow**：默认流程**不生成测试**；本技能是按需补充，不阻塞主流程。产物 `5.3-需求覆盖报告`（静态结构核对）与本技能报告（运行时行为验证）**互不替代**。
- **java-code-standards / database-standards**：生成用例 / 执行器时按需加载。

## 使用要求

生成任何验收工具前，先按 `standards/case-design.md` 设计用例（核心业务场景优先），再按 `standards/runner-standards.md` 落地执行器；执行后报告按 `templates/验收测试报告.md` 输出，失败项必须分类并附服务端日志摘录。
