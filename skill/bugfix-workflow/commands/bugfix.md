# Bugfix（缺陷修复）

## 输入

- bug 描述 / 复现入口（路径、接口、页面、日志）
- 项目现状：是否老项目（先跑 0.5 存量约束对齐）？该模块 docs/ 是否已有 ai-dev-workflow 产物？

## 执行

0. **前置**：确认项目模式——老项目先有 `docs/0.5-存量代码扫描.md`（无则按 ai-dev-workflow `/legacy-scan` 补）；该模块在 docs/ 有历史产物目录 → **先走 ai-dev-workflow 0.8**（0.8-迭代变更影响分析，产物同步不豁免），再进入本流程。

1. **定位与复现**：
   - 确认涉及模块/功能/文件
   - 最小复现步骤：输入 + 操作 + 期望 vs 实际 + 报错原文 + 相关日志；能复现才继续（不能复现 → 说明证据缺口，向用户补充信息，不猜着改）

2. **assess 根因（禁止盲试）**：
   - 读相关代码 + grep/ast-grep + 日志，形成**根因假设**
   - 用证据验证假设（代码路径 / 数据样例 / 日志时间线），验证不过 → 换假设，禁止直接动手改
   - 记录根因 + 为什么 bug 没被既有测试拦住（可触发补测试）

3. **影响面与产物同步判断**：
   - 修复是否触碰需求/契约/验收口径？→ 是：回 ai-dev-workflow（0.8/修整），不属于 bugfix
   - 该模块 docs/ 有 1.1/3.x 产物且实现与产物不一致 → 修复后按 0.8 同步产物
   - 划清"本次要改的最小范围"，列出不改的相邻代码

4. **fix（最小修复）**：
   - 只改根因相关代码，禁止顺手优化/重构/无关清理
   - 本次新增/修改代码：全量注释（comment-standards）+ 方法级日志（java-code-standards §1.6）

5. **verify（防回归）**：
   - 补 1 条防回归测试（先跑红 → 修复后绿），方法命名按 test-standards
   - 相关功能回归：手动/自动跑受影响验收场景 + 关联调用方
   - 收集证据：测试结果 / 运行日志 / 关键文件:行号

6. **兜底与沉淀**：
   - 加载 **check-standards** skill 对本次改动核对（注释/日志/规范逐项附证据），未到位项先向用户确认补齐
   - 修复单落盘 `docs/<模块>/bugfix-<YYYYMMDDHHMMSS>.md`
   - 坑记入 `docs/experience.md`（若判断跨模块通用 → 标 `[HARD] 建议固化进规范/check-standards`，人工走家族固化流程）

## 输出

- 修复单 `docs/<模块>/bugfix-<YYYYMMDDHHMMSS>.md`（模板 `templates/bugfix-修复单.md`）
- 代码改动（最小）+ 防回归测试 + 核对结论

## 完成标准

- [ ] 已复现（步骤/输入/报错/日志证据），根因已验证（非猜测）
- [ ] 影响面与产物同步已判断（有 docs 产物 → 走 0.8 或明确无需同步）
- [ ] 最小改动完成，本次代码全量注释 + 方法级日志
- [ ] 防回归测试 1 条（先红→绿）+ 相关功能回归证据
- [ ] `/check-standards` 兜底核对完成（未到位项确认/补齐）
- [ ] 修复单落盘，经验按需写入 docs/experience.md
