# 功能清单总览 - <模块名>

> 使用说明：这是第 ① 步"需求分析"的产物模板。**这一步决定需求是否被完整实现**——拆漏一个需求点，后续全链缺失。
> 填写要点（按序）：
> - **先做需求准入**（feature-list 第 0 步）：需求分档（A 结构化完整 / B 有模糊 / C 碎片化先补文档）+ 验收基线确认（哪份文档哪个版本 + 有无口头补充）→ 写入速览框与模块信息表
> - **再过滤非 Java 服务端需求**：前端页面/移动端/小程序/其他语言服务端等 → 不拆功能项，记入下方"非 Java 服务端需求（已过滤）"表
> - **列需求点清单**：需求文档逐条拆成需求点（编号 + 描述 + 来源），先穷尽需求再设计功能
> - **拆功能项**：每项 = 一个可独立验收的用户可感知能力，标注"承接需求点"
> - **需求覆盖核对**：每个需求点有承接（功能项 / 已过滤 / 延后），无静默消失
> - **产物确认后必须过 `/req-gate`（1.2 需求质量核对）**：回读原文逐节核对 + 跨节矛盾扫描 + 术语↔码值对齐，过闸后才进入 1.3 澄清
> - **类型**：Controller（HTTP 接口）/ Listener（MQ 消费者）/ Job（定时任务）/ 无入口（配置/工具，仅写通用章节）/ 其他（须注明触发方式）
> - **优先级**：P1（本期 MVP 必须）/ P2（应该，后续版本）/ P3（可选）
> - **依赖**：填写依赖的功能项编号，无则写 —
> - **验收标准**：每条 = **GIVEN-WHEN-THEN 三段式**——GIVEN（前置状态/数据/条件）→ WHEN（用户操作/接口调用/触发）→ THEN（可观测结果/状态变化），禁止形容词（"流畅/合理/正常"）、禁止只写"输入→结果"无前置、禁止"实现 XX 功能"（示例与弱→强写法见下）

## 粒度标准与正反例

> 一个功能项 = 一个**可独立验收的用户可感知能力**——一个 HTTP 端点 / 一个 MQ 消费逻辑 / 一个 Job / 一组内聚的 CRUD（同实体多端点合并一项）。

| 判定 | 示例 | 问题 |
| :--- | :--- | :--- |
| ✅ 正例 | "订单创建"一项 = POST /order（含金额计算） | 可独立开发/测试/验收 |
| ✅ 正例 | "订单 CRUD"合并创建/查询/详情/取消（同实体内聚） | 边界内聚为 OrderController，方案合并写 |
| ❌ 拆太细 | 订单创建拆成"创建接口 + 金额计算 + 库存校验"三项 | 无法独立验收，任务粒度失控 |
| ❌ 拆太粗 | "订单模块"整个作为一项 | 无法验收，依赖混乱 |

## 验收标准写法（弱 → 强，强 = GIVEN-WHEN-THEN 三段式）

| 写法 | 示例 | 判定 |
| :--- | :--- | :--- |
| ❌ 弱 | "实现订单创建" / "订单创建可调通" / "创建流程顺畅、金额合理" | 不可验证 / 形容词不可观测，无法翻译成测试 |
| ❌ 缺前置 | "POST /order → 返回订单号、状态 PENDING" | 只写"输入→结果"，无 GIVEN 前置，测试无法造数据 |
| ✅ 强 | "GIVEN 已登录、商品存在且库存充足；WHEN POST /order 提交合法参数；THEN 返回订单号、订单落库状态 PENDING、金额=单价×数量-优惠" | GIVEN-WHEN-THEN 三段齐全、THEN 可观测，直接翻译成 4.2 测试用例（GIVEN=造数据，WHEN=调接口，THEN=断言） |

> **多态写法**：一个验收标准含多态（合法/非法/边界）时，用多条"GIVEN…WHEN…THEN…"以分号/分号分段并列（见功能项 #1 示例），每条仍保持三段式；禁止用"非法参数 → 报错"这类省略 GIVEN 的写法。
