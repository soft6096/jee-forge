# AI 编码提示词模板

> 使用说明：这是第 ⑤ 步的产物模板。把本文件内容（填好占位符）+ `任务拆解.md` + 项目约束 + 技术方案一起发给编码 Agent。
> 这是"防骗绿"的最后防线：测试是你的标尺，Agent 只负责让它变绿。
> 示例为**订单模块**，替换 <占位符> 后直接使用。

---

## 提示词正文（复制以下内容，替换 <占位符>）

```
你是本项目的编码 Agent。按 任务拆解.md 顺序实现，目标：让全部测试变绿。

## 背景
- 项目：电商后台服务
- 功能：订单管理（US-001）
- 技术方案：docs/订单模块V1.2.0-20260824103000/3.1.1-订单创建-技术方案.md
- 任务清单：docs/订单模块V1.2.0-20260824103000/4.1.1-订单创建-任务拆解.md
- 项目约束：docs/订单模块V1.2.0-20260824103000/2.1-项目约束.md（必须逐条遵守）

## 硬性约束（不可协商）
1. 测试文件是验收标准：禁止修改断言、禁止删除测试、禁止给测试加 @Disabled
2. 严格按 Phase 顺序：先数据层 → 再公共组件（0.5）→ 再业务 → 再接口/消费/调度
3. 必须遵守《项目约束》的全部规则（逐条对照，含"注释规范"与"公共组件规范"章节，违反即不合格）
4. **生成的代码必须遵守约束文件约定**：写任何代码前先对照项目约束。标准模式遵守规范 skill 约定（Java → java-code-standards（命名/分层/集合 xxxList/Service 接口方法禁 public 修饰符/单字母禁 + OpenAPI 注解 @Tag/@Operation + 全类 @Slf4j + logback-spring.xml）+ comment-standards（全量注释 + 步骤注释）；SQL/表/MyBatis-Plus → database-standards（简单查询用 Wrapper 禁 XML，手写 SQL 一律 XML 禁注解 SQL）；pom/依赖/多模块 → build-standards（springdoc/knife4j 必配））；**存量适配模式遵守老项目约定（包结构/返回体/命名/中间件对齐老代码），规范 skill 仅在无对应约定时兜底**。生成物不符合约束即不合格、需返工
5. 每个任务完成后独立提交（commit message = 任务 ID + 描述）
6. 测试红时先排查实现，禁止"改测试迁就实现"
7. 不实现 任务拆解.md 之外的东西（不做"顺手优化"）；Phase 0.5 列出的公共组件必须实现并被复用点调用/继承。编码中发现设计外的重复逻辑：不擅自抽取，在该处注释 `// TODO(收敛): 与 Xxx 重复，待抽公共`，由验收阶段统一处理
8. 写代码时**同时生成注释**（同 pass，不要事后补）：注释内容从技术方案的接口定义/约束/验收场景派生，禁止编造；**全量注释，禁止大段代码无注释**——所有类/字段/方法（**含抽取出来的 private 辅助方法**）必须有 Javadoc（存量适配模式同样适用，不因老项目注释稀疏豁免）；**每个方法写完后立即自检：编号步骤注释覆盖到方法最后一行——尤其方法后半段与深层嵌套（≥3 层 if/for/try）分支与抽取方法，这是长代码生成最易漏注释的区域**
9. 注释必须遵守《项目约束》"注释规范"章节（全量注释：所有类/变量/方法必须有注释、方法体 ≥2 个逻辑步骤编号步骤注释、// WHY: 解释动机、禁止逐行翻译式注释）——抽取方法（buildXxx/convertXxx/validateXxx 等）与主方法同等要求
10. **写代码时同步生成日志**（遵守《项目约束》"日志规范"章节 + java-code-standards `00-common/04-logging-standards.md` §1.6 方法级日志覆盖）：**每个业务方法（Controller/Service/ServiceImpl/Job/Listener，public + private 抽取方法）方法体内 ≥1 条 INFO/WARN/ERROR 业务日志**（**`log.debug` 不算**——线上不输出，不能替代业务日志）——入口记入参摘要（方法名 + 关键入参）、关键分支/阶段有 INFO、结果返回前有日志、异常记 ERROR 带堆栈；**大段逻辑（≥10 行）无 INFO/WARN/ERROR = 不合格**（纯 getter/setter/单行透传可豁免，注明原因）；**每个方法写完后立即自查"本方法体内是否有 log 调用"**（存量适配模式同样适用，不因老项目日志稀疏豁免）
11. 收尾阶段自查注释、日志、权限、事务、幂等、防重入、重复代码（**自查不等于规范核对通过**——全量核对由 5.2 独立执行）
12. **编码完成即停，不自行执行全量规范核对**：本步职责 = "让测试绿 + 逐任务独立提交 + 编码中自查"。**全量规范核对（全部核对项（无级别之分，含方法级注释/日志全覆盖））由 5.2 `/check-standards` 独立执行**（防"自己核自己"骗绿）——编码完成后停下并报告，**禁止自行声称"已通过规范核对"、禁止跨过 5.2 直接进入验收**（5.3 `/accept` 前置检查 `5.2.<功能项序号>-<功能名>-规范核对报告.md`，不存在即拒绝执行）

## 执行步骤
1. 阅读 任务拆解.md、技术方案、项目约束
2. 按 Phase 顺序逐任务实现（先数据层 → 公共组件 0.5 → 契约测试跑起来 → 业务 → 接口）
3. 每完成一个任务：运行测试，记录结果，独立提交
4. 全部任务完成后：跑全量测试（全绿）→ **停下，报告完成**（附测试结果汇总 + 逐任务提交记录）→ 由 `/check-standards`（5.2）独立执行规范核对 → 报告获用户确认后 → 才进入 `/accept`（5.3）验收——**编码 Agent 不自行执行全量核对、不输出验收报告**

## 完成后输出
1. 测试结果汇总（通过/失败，附测试命令与输出）
2. 完成报告（明确"编码完成，待 5.2 `/check-standards` 规范核对"——**不输出规范核对报告/验收报告，那是 5.2/5.3 的产物**）
3. 遗留问题清单（如有）
```

## 给编码 Agent 的补充约定（选填）

### 关于测试
- 契约测试文件是验收标准，属于你的**只读输入**，不是你要实现的代码
- 遇到测试红，先读测试理解期望行为，再修实现
- 若你认为测试本身有 bug（非实现问题）→ 停下来询问，不要自行改测试

### 关于提交
- commit message 格式：`T00X: 任务描述`（如 `T004: 订单创建Service实现`）
- 每个任务一个 commit，便于回滚和 review

### 关于范围
- 只做 任务拆解.md 里列出的任务
- 发现 任务拆解.md 与项目约束冲突 → 停下来询问，不要自行决定
- Phase 0.5 公共组件是任务，属于你要实现的范围；发现任务外的重复逻辑 → 标记 `// TODO(收敛)` 不抽取，验收阶段处理

### 关于注释
- 注释与代码**同一轮生成**：写方法时基于技术方案同步写 Javadoc/WHY，不要写完代码再回头补
- **覆盖所有方法含抽取方法**：主方法写完抽出的 private 辅助方法（buildXxx/convertXxx/validateXxx），抽完立即补类注释（如嵌套类）+ 方法 Javadoc + 方法内步骤注释/日志——抽取方法是最易漏注释/漏日志的位置
- **长方法分段注释**：方法超过 ~20 行时按逻辑段落写编号步骤注释（`// 1.` `// 2.` …），深层嵌套（≥3 层 if/for/try）分支前加一行注释说明该分支意图——不要只给方法开头几行加注释、后半段裸奔
- 注释内容拿不准怎么写 → 从技术方案对应段落取依据；**技术方案也没有 → 询问，不编造**（"写错比不写更糟"仅指禁止编造，不豁免全量覆盖义务）

### 关于关键规范核对（编码 Agent 不自评——核对由 5.2 `/check-standards` 独立执行）

**编码 Agent 不做全量规范核对**（防"自己核自己"骗绿）。编码中只需自查注释/日志（见硬性约束 8/9/11）；收尾时**停下报告完成**，交由 5.2 `/check-standards`（加载 **check-standards** skill：全部核对项（无级别之分，含方法级注释/日志全覆盖）+ 标准 grep/ast-grep 指令 + 证据要求见其 SKILL.md）独立核对并产出 `5.2.<功能项序号>-<功能名>-规范核对报告.md`，报告获用户确认后才进入 5.3。以下自查要点供编码 Agent **自查时参考**（确保编码阶段不把明显问题带进 5.2）：

| # | 核对项 | 判定标准（全部满足才算 ✅） | 规范出处 |
| :---: | :--- | :--- | :--- |
| 0a | **方法级注释全覆盖（自查第一优先）** | **每个写的方法（public + private 抽取方法，含 buildXxx/convertXxx/validateXxx）写完立即自查**：方法前有 Javadoc（功能 + @param/@return）；方法体 ≥2 步骤有编号注释；抽取方法同样有注释——**一个方法写完没注释 = 不合格，当场补**（不拖到收尾） | comment-standards `standards/comment-standards.md` |
| 0b | **方法级日志全覆盖（自查第一优先）** | **每个写的方法（public + private 抽取方法）方法体自查：是否有 `log.info/warn/error` 调用（`log.debug` 不算——线上不输出）**——入口/关键分支/结果 ≥1 条 INFO/WARN/ERROR；**开头 1 条 debug 或 1 条 INFO 但中间 10+ 行查库/循环/组装无 INFO = 不合格当场补**；纯 getter/单行透传豁免；异常处 ERROR 带堆栈 | java-code-standards `00-common/04-logging-standards.md` §1.6 |
| 1 | OpenAPI/Swagger 支持 ⚠️选型敏感 | ① 接口模块 pom 已引 springdoc-openapi（/knife4j），版本由 BOM 管理（**按 2.1 选型**：老项目 Swagger2 则按 @Api/@ApiOperation 体系，纯 Apifox 约定按老约定）；② 每个 Controller 类有 `@Tag`、方法有 `@Operation`；③ 每个 DTO/VO 字段有 `@Schema`；④ 文档开关按环境配置（online 关闭） | build-standards `standards/dependency-standards.md`；java-code-standards `01-java/api-doc-standards.md` |
| 2 | 日志支持 ⚠️选型敏感 | ① 日志框架按 2.1 选型：Logback → `resources/logback-spring.xml` 已提供（控制台 + 滚动文件 + 环境级 level，参考 `04-templates/logback-spring.xml`）；Log4j2 → log4j2 配置存在且无 logback 并存（老项目按 0.5 扫描框架）；② 全类 `@Slf4j`（Controller/Service/Job/Listener）；③ 无 System.out、无字符串拼接日志；④ **每个业务方法（含 private 抽取方法）方法体内 ≥1 条 INFO/WARN/ERROR 日志**（debug 不算；开头 1 条日志但中间关键逻辑无 INFO = ❌；大段逻辑 ≥10 行无 INFO = ❌，见 `04-logging-standards.md` §1.6） | java-code-standards `00-common/04-logging-standards.md` |
| 3 | SQL 全在 XML ⚠️选型敏感 | ① 无注解 SQL（`@Select`/`@Insert`/`@Update`/`@Delete`/`<script>`）；② 手写 SQL 全部在 `resources/mapper/XxxMapper.xml`，namespace 与接口一致；③ 接口方法均有 XML 或 BaseMapper 实现，无空方法（老项目 ORM/约定不同按 0.5 数据访问约定） | database-standards `mybatis-plus/mybatis-xml-standards.md` |
| 4 | 详细设计 SQL 注释 | 技术方案《数据模型与 SQL》章节所有 SQL 带注释：查询/DML 每条 `--` 注释（用途 + 归属 Mapper 函数 + 关键条件），DDL 每字段 COMMENT | ai-dev-workflow `templates/3.0-技术方案-通用骨架.md`；database-standards `standards/sql-standards.md` |
| 5 | DDL 字段注释 | 建表语句**每个字段** `COMMENT '...'`（含义 + 枚举取值/单位/时区约定）+ 表级 `COMMENT`；无裸字段无注释 | database-standards `standards/table-design-standards.md` |
| 6 | JSON 入参/出参产物 | ① `3.<功能项序号>.2-<功能名>-接口清单（前后端通用）.md` 已生成（Controller 类型功能项方案后同步生成）；② 每个接口有 URL + 方法 + **JSON 入参示例** + **JSON 出参示例（成功/失败）**；③ 内容与技术方案一致；无 HTTP 接口功能项 → 标注"跳过" | ai-dev-workflow `templates/3.4-接口清单-前后端通用.md` |

> 其余核对项（事务 rollbackFor / SQL 注入 / UPDATE-DELETE 带 WHERE / 统一返回体 / 密码加密 / 分页上限 / 场景化项等）完整检查指令见 **check-standards** skill 的 SKILL.md——全部核对项无级别之分，任何一项未执行都要在 5.2 停下与用户确认。

> [!WARNING] 禁止"没做就声称做了"
> 自查是**实际检查产出**（grep 依赖/注解/XML、打开 logback-spring.xml、核对 DDL、查注释覆盖率），不是凭记忆回答。发现遗漏 → 编码阶段直接补齐（这是编码 Agent 职责内的事）。**全量核对与最终判定由 5.2 `/check-standards` 独立执行，编码 Agent 不自评"已通过规范核对"。**

## 完成标准自检

- [ ] 提示词中 任务拆解.md、项目约束、技术方案的路径都已填
- [ ] 编码 Agent 收到的是"让测试变绿"的指令，不是"实现 XX 功能"
- [ ] 硬性约束 12 条完整包含（含规范 skill 加载要求 + 注释/日志不豁免 + **编码完成即停、不自评规范核对**）
- [ ] 明确告知编码 Agent：全量规范核对由 5.2 `/check-standards` 独立执行，编码完成后停下报告，不输出核对报告/验收报告
- [ ] 要求了测试结果汇总作为输出（含完成报告）
