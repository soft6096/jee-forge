# 项目约束（存量适配）- <模块名>

> 使用说明：这是第 ② 步"技术架构"的**存量适配模式**产物模板。**适用范围**：老代码基础上迭代新需求，已走 0.5 `/legacy-scan` 且用户选择**跳过存量优化**。
> **核心口径**：新需求代码按**老项目实际约定**写，不被规范 skill 的标准答案带偏——包结构、返回体、命名风格、中间件全部对齐老代码。规范 skill（java-code-standards / comment-standards / database-standards）**仅在老项目无对应约定时兜底**。
> **与老项目约束文件的关系（去重引用，不复制）**：老项目**有**项目级约束文件（AGENTS.md / CLAUDE.md / GEMINI.md / README 规范章节等，**以实际存在为准，不限于某一文件名**）→ 文件里**已有的约束在本文件直接引用**（"按老项目约束文件《XX》执行"，不复制内容），**只把文件里没有的约定补充进本文件**；老项目**无**此类文件 → 扫描到的约定**全部写入本文件**（本文件是本次开发的唯一约束来源）。
> 填写要点：
> - 每条约束必须**能检查对错**（是/否可判定），禁止"尽量""建议""最好"等软约束
> - **每条约束标注老代码出处**（类名/配置项/目录路径），AI 编码时有据可查
> - 版本号/账号写死（与老项目实际配置一致，不是"标准答案"）
> - AI 编码时逐条对照，违反即为不合格

## 注释规范（存量适配）

> **新代码全量注释（强制，不因老项目注释少而豁免）**：本次新增/修改的代码**必须按 comment-standards 全量注释**——所有类（DTO/VO/Config 等，仅示例非穷举）类注释、所有变量/字段注释、所有方法（含测试方法）注释（@param/@return 写业务含义）、方法体 ≥2 个逻辑步骤编号步骤注释、复杂逻辑 // WHY:、禁止大段代码无注释。**老项目存量代码注释稀疏不是新代码豁免的理由**——老代码是历史，新代码必须达标。
> **本模板仅用于"跳过优化"场景**：用户在 0.5 选择了 comment-standards 优化 → 走标准模板（`2.1-项目约束.md`，按 comment-standards 全量注释），不用本模板。
> 注释规则细节见 comment-standards skill（`standards/comment-standards.md`），AI 编码时加载，逐条对照其强制规则与自检清单。

## 日志规范（存量适配）

> **新代码日志完善（强制，不因老项目日志少而豁免）**：本次新增/修改的代码**必须按 java-code-standards 日志规范（`00-common/04-logging-standards.md`）完善日志**：
> - 全类 `@Slf4j`，禁止 `System.out` / 字符串拼接日志
> - **请求入口（Controller）记录入参摘要 + 耗时，出口记录结果**（见 04-logging-standards 最佳实践）
> - **关键业务节点记 INFO**：状态变更、下单/支付/取消、定时任务开始/结束/完成、消费处理完成
> - **异常必须记 ERROR 且带堆栈**（`log.error("msg, orderId={}", orderId, e)`，异常对象作最后参数）；catch 块禁止空吞
> - 关键日志带业务上下文 ID（订单号/用户 ID）
> - 老项目存量代码日志稀疏不是新代码豁免的理由——新代码该记日志的地方必须记。
> 日志规则细节见 java-code-standards `00-common/04-logging-standards.md`，AI 编码时加载，逐条对照其强制规则与自检清单。
