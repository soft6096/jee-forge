# 项目约束 - <模块名>

> 使用说明：这是第 ② 步"技术架构"的产物模板。约束是整个流程的"宪法"——第 ③ 步技术方案、第 ⑤ 步 AI 编码都必须逐条对照。
> **两种模式**：
> - **标准模式（本模板）**：新项目 / 未走 0.5 存量扫描 / **走 0.5 且选择按规范优化**——按规范 skill 生成约束，模板如下；走 0.5 选优化时，**中间件版本/账号等老项目事实仍对齐**（引用 `0.5-存量代码扫描.md` 中间件清单）。**生成后同步写入项目根 `AGENTS.md`**（不存在则创建，或追加到已有规范章节），成为整个项目的长期规范（后续所有模块开发都遵守，不限于本次）。
> - **存量适配模式**：老代码迭代新需求、已走 0.5 且用户选择跳过存量优化——按 `0.5-存量代码扫描.md` 的老项目约定生成约束（包结构/返回体/命名/中间件对齐老代码），模板见 `2.1-项目约束-存量适配.md`，**不要用本模板**；该模式仅本次开发流程生效，不写入 AGENTS.md。
> 填写要点：
> - **分层**：**能检查对错**（grep/ast-grep 可判定）的 → 写入下方"硬性约束"表（验收红线，check-standards 兜底核对）；**判不了对错**的团队取向/风格 → 单独写入"软取向 / 背景约定"小节（AI 背景遵循，**不参与自动核对**），**禁止混进硬性约束表**（混入无法判定的条目会稀释核对）
> - 每条硬性约束必须**能检查对错**（是/否可判定），禁止"尽量""建议""最好"等软约束
> - 版本号写死：Spring Boot 3.2.x 而不是"新版本"
> - AI 编码时逐条对照，违反即为不合格
> 下方为**示例项目**（RuoYi-Vue 系）的完整约束，复制后替换成你的技术栈。
>
> 📌 **样式要求**：速览框 / 对齐表格统一按 `通用-中间产物-MD样式规范.md`。

## 硬性约束（AI 编码时必须遵守）

| # | 约束 | 违反判定 |
| :---: | :--- | :--- |
| 1 | 统一使用 MyBatis-Plus，禁止原生 JDBC | 出现原生 JdbcTemplate/JDBC 代码 |
| 2 | 所有新增接口必须加 @RequiresPermissions 权限注解，权限码格式 `模块:资源:操作` | 接口无权限注解或格式不符 |
| 3 | 数据库操作统一走 Service 层，Controller 禁止直接调用 Mapper | Controller 注入 Mapper |
| 4 | 涉及多表写入的方法必须 @Transactional，事务只放在 Service 层 | 多表写无事务 / Controller 加事务 |
| 5 | 返回体统一使用 `Response<T>`（code/message/data），禁止直接返回 Map；分页用 PageResult | 返回 R/Map/其他包装 |
| 6 | 实体类字段命名统一驼峰，表字段统一下划线；表名小写+下划线+**统一业务前缀**（规则见 database-standards `table-design-standards`） | 命名不规范 |
| 7 | 禁止 System.out.println，统一使用 lombok @Slf4j 的 log；日志框架按技术架构选型 **Logback**（默认）——全类 @Slf4j，项目提供 logback-spring.xml（控制台+滚动文件+环境级 level） | 出现 System.out / 未按选型引入日志框架 |
| 8 | 新增接口必须 OpenAPI 注解：Controller 类 `@Tag`、方法 `@Operation`、DTO/VO 字段 `@Schema`（springdoc/knife4j 依赖见 build-standards；团队用 Apifox 时注解照写供导入）；文档开关 online 关闭 | 接口无注解 / 依赖缺失 / online 未关 |
| 9 | Listener 消费必须做幂等处理（唯一键或状态位），且手动 ACK | 无幂等 / 自动 ACK |
| 10 | Job 必须防重入（Redis 分布式锁或状态位），批处理单次不超过 500 条 | 无锁 / 批量超限 |
| 11 | 所有时间字段用 DATETIME，禁止字符串存时间 | 时间用 VARCHAR |
| 12 | 金额字段用 DECIMAL(10,2)，禁止 float/double | 金额用浮点 |
| 13 | 逻辑删除统一 `deleted`（0-未删 1-已删，见 database-standards `table-design-standards`），禁止物理删除业务数据 | 物理 DELETE / 逻辑删除字段不一致 |
| 14 | 业务异常统一抛 `BusinessException(ErrorCode, message)`，错误码集中定义，由全局异常处理器转换；禁止 try-catch 后吞掉（见 java-code-standards 异常规范） | 空 catch / 吞异常 / 裸 RuntimeException |
| 15 | **写接口必须幂等**（下单/支付回调/批量提交等可重试/重复提交场景）：唯一键约束、幂等令牌（防重提交）或 Redis SETNX；幂等键持久化与业务处理同事务；禁止重复双写（见 java-code-standards `01-java/distributed-standards.md`） | 写接口无幂等方案 / 幂等键与业务不同事务 |
| 16 | **分布式事务取舍**：跨服务写入禁止硬上 2PC/XA，默认最终一致（MQ 事件驱动 + 幂等消费 + 对账补偿）；补偿必须有（正向配反向且补偿幂等）；事务内禁止远程调用/长循环（见 java-code-standards `01-java/distributed-standards.md`） | 跨服务强一致硬上 2PC / 无补偿 / 事务内远程调用 |

> [!WARNING] 硬性约束是验收红线
> 每条约束都能判定对错（见"违反判定"列），AI 编码时逐条对照，违反即为不合格。

## 软取向 / 背景约定（不参与 check-standards 核对）

> 这类条目**判不了对错**（无法用 grep/ast-grep 判定），但希望 AI 编码时作为背景取向遵循。**不要把它混进硬性约束表**——硬性约束是验收红线，混入无法判定的条目会稀释核对；也不要把它写成硬规则（否则变成"无法检查的伪红线"）。每条软取向写清"遵循场景"；未写到的场景按硬性约束 + 规范 skill 执行。**无软取向 → 整节删除并注明"无"。**

| # | 软取向（AI 背景遵循，不强制判定） | 遵循场景 / 说明 |
| :---: | :--- | :--- |
| S1 | 命名尽量贴合业务语义（状态值用 `PENDING/PAID` 枚举而非裸 0/1） | 可读性倾向，判不了对错（枚举 vs 裸值已有硬约束处除外） |
| S2 | 新增逻辑优先复用/扩展 `common/` 已有组件，少新起炉灶 | 与硬约束 #20~23 互补，覆盖边界情形 |

## 注释规范（AI 编码时随代码生成）

> **注释规范见 comment-standards skill**（`standards/comment-standards.md`），AI 编码时加载，逐条对照其强制规则与自检清单。本流程不复制注释规则，避免双份维护漂移。
