# 存量注释补全

为已有代码生成或补全注释。核心原则：**有 spec 走 spec，无 spec 降级为事实注释，猜不出的意图宁缺毋滥**。

> 完整执行规则与注释规范见 **comment-standards** skill（`standards/gen-comments-workflow.md` + `standards/comment-standards.md`），本命令为流程入口。
> 若存量代码同时日志不完善（无 @Slf4j / System.out / 关键节点无日志），注释补全后**再运行 `/gen-logs` 补日志**（本命令只覆盖注释，不碰日志）。

## 输入

- 目标代码路径（文件/目录/模块）
- 技术方案 md（存在时自动走 `--from-spec`，否则 `--from-code`）

## 两种模式

### `--from-spec`（有技术方案，优先）

代码有对应 3.x 技术方案 md → **从 spec 派生，不猜**：

1. 读技术方案 md（接口清单/JSON 示例/验收场景/注释要求章节）
2. 匹配代码元素到 spec 项
3. 从 spec 抄业务含义、约束条件、@throws 场景生成 Javadoc
4. 匹配不上 spec 的代码 → 对该部分降级为 `--from-code` 处理

### `--from-code`（无 spec，仅事实注释）

无技术方案 → 只写"有据"注释，按可信度分级：

| 注释内容 | 来源 | 策略 |
|---|---|---|
| @param | 签名 + 参数名 + 校验代码 | 直接写 |
| @return | 返回类型 + return 语句 | 直接写 |
| @throws | throw / 调用链 | 直接写 |
| 业务意图（为什么） | 调用方 + 测试断言 + 命名 | 推导得出才写；**否则不写** |

## 执行规则（硬性约束，不可协商）

```
1. 遵守《项目约束》"注释规范"章节：全量注释（所有类/变量/方法必须注释、
   @param/@return 写业务含义、方法体 ≥2 个逻辑步骤编号步骤注释、禁逐行翻译式注释）
2. 已有合格注释不覆盖，只补缺失或不合格的
3. 禁止修改业务逻辑，只增删注释
4. 猜不出的意图不写，禁止编造行为描述（宁缺毋滥）
5. 每个文件完成后独立提交（commit message = 补注释: 文件路径）
6. 先扫后补（防长文件漏注释）：补注释前先扫描产出缺口清单（文件:行号:元素类型:元素名:缺口描述，
   见 comment-standards skill `standards/gen-comments-workflow.md`「缺口扫描」章节——ast-grep/LSP 列结构清单
   + 检查声明上方有无 /** 文档注释），按清单逐个补齐，禁止通读全文件凭印象补
7. 全部补齐后重跑扫描复核：缺口清单清零才算完成，残留项不静默跳过
```

## 输出

- 补全注释的代码
- 注释核对结果（复用 5.3-验收报告.md"注释核对表"6 项）

## 完成标准

- [ ] 公开 API 全部有 Javadoc（按注释规范）
- [ ] 无逐行翻译式注释、无遗漏注释项（类/字段/方法/步骤全覆盖）
- [ ] 缺口清单清零（先扫后补：扫描产出清单 → 逐个补 → 重扫复核无残留）
- [ ] 注释与代码事实一致（抽查，禁止编造意图）
- [ ] 未修改任何业务逻辑
- [ ] 已有合格注释未被破坏
