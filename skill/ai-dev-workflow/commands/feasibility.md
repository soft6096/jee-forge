# 需求可行性评估（可选前置闸门）

**普通需求不要走本步**——只有命中下方"风险信号"的需求才建议触发，由你拍板是否执行。跑完一页速评后仍回到流程正常入口（1.1 `/feature-list`，超大/跨模块按需先 0.9 `/req-intake`）。

## 风险信号判定（AI 判定 + 人确认是否执行）

命中任一即建议触发（**未命中 → 说明无需评估，直接进 1.1**，禁止为走流程而走流程）：

- [ ] 涉及未用过的外部系统 / 中间件 / 第三方 SDK（对接可行性未知）
- [ ] 技术选型或实现路线有争议（多条路，不知道走哪条）
- [ ] 需求方向新、成本不清（首次进入的业务域 / 体量模糊 / 投入产出不明）
- [ ] 其他你认为值得先评估的点（写明）

> AI 命中信号后，向用户展示命中项并确认"是否执行可行性评估"。**用户选跳过 → 直接进 1.1**。

## 执行

1. **读事实**：读取需求文档/相关产物（`ls docs/` 实查是否有相关旧产物 / 0.5 存量扫描结论 / 项目约束等），定位涉及代码的关键点。
2. **自查关键未知**：能读码/查文档查清的当场查清（如现有表结构、公共组件、已接入中间件）；查不到的列为"需人提供"。
3. **一页速评**：按模板 `templates/0.6-需求可行性评估.md` 产出（风险扫描表 + 关键未知结论 + 体量粗估 + 备选路线 ≥2）。
4. **结论 + 人拍板**：
   - 🟢 **go** → 进 1.1 `/feature-list`（超大/跨模块按需先 0.9 `/req-intake`）
   - 🟡 **需澄清** → 待澄清问题清单交人逐项裁决（AI 给建议默认值），澄清后回本环节定 go/kill
   - 🔴 **kill** → 不做，理由存档（写明"何时值得重启"）
5. **回写**：结论与裁决写入产物；go 后再走正常入口。

## 输出

- `docs/0.6-需求可行性评估.md`（同一批再次评估 → `docs/0.6-需求可行性评估-<YYYYMMDDHHMMSS>.md`）

## 完成标准

- [ ] 风险信号判定明确：命中项已展示并获人确认执行 / 未命中直接进 1.1
- [ ] 已有事实均实查（读码/文档/ls），无凭空断言
- [ ] 一页速评产出（风险扫描无空行 + 关键未知有结论 + 体量粗估 + 备选路线 ≥2）
- [ ] 结论已获人拍板（go / 需澄清 / kill）；🟡 待澄清项逐项裁决后才有放行
- [ ] go 后按正常入口进 1.1（超大/跨模块先 0.9）；kill 的理由与重启条件已存档
