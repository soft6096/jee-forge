# 需求质量核对（req-gate，强制闸门）

在 **1.1 功能清单之后、1.3 澄清之前**执行。功能清单只证明"需求点被拆成功能项"，**不证明"需求点本身拆对了"**——需求点由 AI 拆解，若拆解时误读/收窄/选了矛盾的一侧，覆盖核对照样全绿。本闸门对需求文档原文做三道**独立核对**，把"拆错的需求"拦在方案与编码之前。

## 输入

- 1.1 功能清单（`docs/<模块名>V<版本号>-<YYYYMMDDHHMMSS>/1.1-功能清单.md`，目录名见 1.1 产物）
- **需求文档原文**（本闸门强制回读原文，不能只依赖功能清单）
- 需求经 0.9 `/req-intake` 整形时：回读基线 = 对应《<模块名>-模块需求.md》，并按其中**来源段落追踪**字段可追溯原始需求文档
- 存量枚举/码值事实源：老项目 → `docs/0.5-存量代码扫描.md`（不存在则**先跑 `/legacy-scan`**，对齐老项目枚举/码值/命名）；新项目 → 项目内已有枚举类/常量类（grep 兜底）

## 执行

**前置**：检查 1.1 产物是否存在；不存在 → 先执行 `/feature-list`。检查需求文档是否已做过**分档与基线确认**（见 feature-list 第 0 步）；缺失 → 先补做并写入 1.1 速览框。

按序执行三道核对，每道产出记录，合并写入 `1.2-需求质量核对.md`：

### ① 需求原文回读核对（防"拆解时误读/收窄范围"）

回读需求文档，**逐节比对**（不是逐条——防 AI 只对"拆出的需求点"负责，漏掉没被拆的段落）：

| # | 原文章节 | 原文要点 | 对应需求点/功能项 | 核对结论 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | §7.3.2 | 表格区含"商品类型"列 | R5（承接） | ✅ 已承接 |
| 2 | §8.2.2 | 跳转目标规则 | — | ⚠️ 无承接，疑似遗漏 |

- 原文有表述但功能清单无对应需求点/功能项 → **遗漏信号**：补需求点或标"已过滤/延后（记原因）"，不允许静默消失
- 功能项验收标准与原文表述不符（口径被收窄/放宽）→ **误读信号**：回退修正功能清单对应项
- 每节结论：✅ 已承接 / ⚠️ 遗漏信号 / 🔧 需修正

### ①·补 验收标准格式核对（GIVEN-WHEN-THEN，强制）

> 1.1 验收标准必须为 **GIVEN-WHEN-THEN 三段式**（写法见 `templates/1.1-功能清单.md`"验收标准写法"）。本步逐条核对格式，防"能跑但不可测/虚"的验收标准混过闸门。

逐条检查 1.1 每个功能项的验收标准：
- 三段齐全：**GIVEN**（前置状态/数据/条件）→ **WHEN**（操作/调用/触发）→ **THEN**（可观测结果/状态变化）
- THEN 可观测：不含"流畅/合理/正常/等"等形容词或不可判定表述
- 多态（合法/非法/边界）未省略 GIVEN（"非法 → 报错"类写法不合格）

| # | 功能项 | 验收标准 | 格式结论 | 修正 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | #1 订单创建 | 合法：GIVEN…WHEN…THEN…；非法：GIVEN…WHEN…THEN… | ✅ / 🔧 缺 GIVEN / 🔧 THEN 不可观测 | 不合格 → 当场回写 1.1 |

> 不合格项 = 🔧 当场回写 1.1 功能清单；全部合格后才进入下一道核对。

### ② 跨节矛盾扫描（防"前后矛盾被静默选边"）

把需求文档中所有**规格性表述**（字段/规则/数值/枚举/口径）提取成清单，**两两交叉核对**冲突——不止逐条读，还要跨章节比对：

| # | 表述 A（章节） | 表述 B（章节） | 冲突点 | 处理 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | 7.3.1 列表区无"商品类型"列 | 7.3.2 表格区有"商品类型"列 | 列表列集合不一致 | 🔲 待 1.3 澄清 |
| 2 | 8.2.2 跳转类型=链接跳转 | 8.2.2 跳转目标=商品下拉 | 跳转目标口径冲突 | 🔲 待 1.3 澄清 |

- 扫描范围：字段口径、数值/单位、状态机流转、枚举取值、界面交互、权限规则、非功能指标（尺寸/容量/性能）
- **禁止静默选边**：发现矛盾不自行挑"好拆的一侧"写进功能清单，一律标 🔲 进 1.3 澄清，由人裁决
- 核对完的功能清单，若存在矛盾项，**不得标"已通过"**——矛盾项全部 🔲 待 1.3 确认后才算过闸

### ③ 术语↔码值对齐（防"需求术语与现有系统不一致"）

提取需求文档中的**业务术语与枚举值**，对照存量事实源建立映射：

| # | 需求术语/取值（章节） | 现有系统枚举/码值 | 来源证据 | 对齐结论 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | "标准商品"（§7.2） | MallProductTypeEnum.PHYSICAL | 0.5 扫描/枚举类 | ✅ 一致 |
| 2 | "跳转链接=商品下拉" | 无对应枚举 | — | 🔲 需澄清是否新增 |
| 3 | "商品状态：在售/下架/删除" | 现有 0/1/2 | ProductStatusEnum | ⚠️ 命名/取值需对齐 |

- 需求术语 ↔ 现有枚举/码值**一一对应**：能对上 ✅；对不上标 🔲（需澄清是否新增枚举，**禁止直接造新枚举**）；同一含义不同叫法 → 记录归一
- 老项目**未跑过 0.5 扫描** → 自动提示先跑 `/legacy-scan`（术语对齐的事实源来自扫描结论）；新项目 → grep 项目内已有枚举/常量类
- 字段命名（Java/数据库）与现有风格不一致 → 记入 🔧 修正，2.1 约束阶段对齐

### ②·补 枚举/状态机械对照矩阵（需求含规格性表格时强制）

> **触发范围**：需求文档含**字段定义/数据字典/状态流转/下拉枚举等规格性表格**时，把第②道从"读着找矛盾"升级为"先抄写归拢、再在归拢结果上找矛盾"（防长文档中同一枚举/状态在多处取值不一致被漏扫）。纯描述性需求（无规格性表格）→ 注明"无规格性描述，矩阵跳过"，不硬凑。

**矩阵 A：枚举一致性矩阵** —— 需求中每个枚举字段一行，列 = 该字段出现的全部位置（字段定义表 / 数据字典 / 页面与流程 / 规则正文），逐格**原样抄值**：

| 枚举字段 | 定义处取值 | 流程/规则处取值 | 结论 |
| :--- | :--- | :--- | :--- |
| 订单状态 | 待支付/已支付/已取消 | 待支付/已支付/已关闭 | 🔲 冲突：定义 vs 流程取值不一致 |
| 活动类型 | A/B | A/B/C | 🔲 冲突：流程处多出 C |

**矩阵 B：状态×动作闭合矩阵** —— 每个有状态的实体一张：行 = 状态枚举全集 + 按钮/流程引用的状态；列 = 「进入它的动作 / 离开它的动作 / 引用它的位置」：

| 状态 | 进入它的动作 | 离开它的动作 | 引用它的位置 | 闭合结论 |
| :--- | :--- | :--- | :--- | :--- |
| 待审核 | 提交 | 通过/驳回 | 审核按钮 | ✅ |
| 已关闭 | — | — | 规则"超时关闭" | 🔲 无进入动作：谁把订单置为已关闭？ |
| （按钮引用）"待验收审核" | — | — | 审核流 | 🔲 不在状态枚举中 |

- 任一格取值不齐 / 状态无入边无出边 / 引用了枚举外状态 → **必出 🔲 进 1.3 澄清**，禁止静默选边
- 抄写结论按原文章节标注出处；两矩阵产出并入 `1.2-需求质量核对.md`（②·补章节）

## 输出

- `docs/<模块名>V<版本号>-<YYYYMMDDHHMMSS>/1.2-需求质量核对.md`（参考模板 `templates/1.2-需求质量核对.md`，含①回读核对表 ②矛盾清单 ③术语对齐表 ④待确认汇总）
- 核对结论回写 1.1 功能清单：🔧 修正项当场修正；⚠️ 遗漏项补需求点/功能项

## 完成标准

- [ ] 需求文档**逐节回读核对**完成：每节有承接或明确"过滤/延后"记录，无静默遗漏（含文档中"无功能项承接"的章节）
- [ ] **验收标准格式核对完成**：1.1 每条验收标准为 GIVEN-WHEN-THEN 三段式且 THEN 可观测（不合格项已 🔧 回写 1.1）
- [ ] 规格性表述**两两交叉**扫描完成：矛盾项全部标 🔲 进 1.3 澄清，**无静默选边**
- [ ] **枚举/状态机械对照矩阵完成**：需求含规格性表格时已产出 矩阵A（枚举一致性）+ 矩阵B（状态×动作闭合），取值不齐/状态不闭合/引用枚举外状态项全部标 🔲；无规格性描述已注明"矩阵跳过"
- [ ] 术语/枚举对照存量事实源建立映射：对不上项已标 🔲（未擅自造新枚举）；老项目未跑 0.5 时已提示/执行 `/legacy-scan`
- [ ] 功能清单已按核对结论修正（误读项回退、遗漏项补充），1.1 产物同步更新
- [ ] 1.2 产物已落盘并**向用户展示确认**：🔲 项全部待 1.3 澄清，**未获确认不得进入 1.3**
- [ ] 需求分档（A/B/C）与验收基线已确认并写入 1.1 速览框（缺失则先补）

- 对应步骤行 → `✅ 已确认`；「当前断点」→ 下一步骤；「变更记录」追加一行（日期/更新人/说明）
- 模块目录尚未创建（0.0 / 0.5 / 0.9 req-intake 等前置阶段）→ 跳过；1.1 建目录时创建 `通用-模块进度与断点.md` 并据已有产物回填
