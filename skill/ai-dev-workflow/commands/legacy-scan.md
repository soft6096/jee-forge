# 存量代码扫描与约束适配

在已有代码库（老项目/历史项目/他人维护项目）上迭代新需求时必做。**先摸清老项目约定，再决定新代码怎么对齐**——新需求代码风格与老项目一致，不被规范 skill 的标准答案带偏。

## 触发场景

- 老代码基础上迭代新需求（需求文档明确提到"在现有 XX 项目上新增 XX"）
- 在了解不多的既有工程里开发新模块（项目现状不明）
- 用户提到"按老项目的风格/规范写""和已有代码保持一致"
- **按流程开发（方式二）自动进入**：入口"开发场景判定"判定为老代码/既有项目迭代 → 本命令自动触发，**进入即弹"是否按规范优化存量代码"决策闸门**

从零新项目跳过本命令，直接 1.1；完整 8 维度体检可另用 legacy-onboarding skill。

## 输入

- 项目路径（代码库位置）
- 需求文档（可先不提供，扫描不需要）

## 执行

1. **扫描老代码（只读，禁止顺手改代码）**，逐项记录证据（文件路径/行号/配置项）：

| 扫描项 | 扫什么 | 怎么扫 | 记录内容 |
|---|---|---|---|
| 包结构与分层 | 业务代码包归属、分层结构、BaseEntity/公共类位置 | `ls src/main/java` 遍历包树 | 新代码放哪个包、controller/service/mapper 归属 |
| 返回体与公共组件 | 统一返回类/分页类/异常处理/工具类/基类 | grep `class R` / `class Response` / `PageResult`、读 common 包 | 返回类类名、包位置、字段结构；可复用组件清单 |
| 命名风格 | Java 类/变量/方法命名、数据库表/字段命名 | 抽样 2-3 个类 + 读建表 DDL | 驼峰/下划线映射、前缀习惯、缩写习惯 |
| 数据访问层约定 | ORM（MyBatis-Plus/MyBatis/JPA）、Mapper XML 习惯、逻辑删除/乐观锁/字段自动填充、BaseEntity 公共字段 | 读 Entity + Mapper + XML | 数据访问写法（新表/新 Mapper 照此写） |
| 接口与错误码 | 接口文档工具（Apifox/Swagger）、错误码体系、权限注解、参数校验 | 读 Controller + 接口文档 + 常量类 | 文档工具、错误码定义位置、权限注解写法 |
| 认证鉴权 | 登录方案（JWT/Shiro/OAuth2）、token 生成/命名、会话管理 | 读 Security/Filter/JWT/登录代码 | 登录与鉴权方式（新接口怎么鉴权） |
| 中间件与基础设施 | 见下方中间件子表 | 读 application*.yml + 现有接入代码 | 版本、账号、接入方式、使用规范 |
| 工程与环境 | 构建工具、Java/Spring Boot 版本、profile 拆分、端口 | 读 pom.xml + yml | 环境基线（新代码编译/运行依赖） |
| 测试基线 | 测试框架、测试目录结构、测试数据准备 | 读 src/test | 新功能测试怎么写 |
| 既有约定 | **项目级约束文件**：AGENTS.md / CLAUDE.md / GEMINI.md / README 规范章节 / 项目规范文档等（**以实际存在为准，不限于某一文件名**）——有无、覆盖哪些约束 | 读项目根文档 + 遍历根目录 | 约束文件清单 + 已覆盖的约束范围；2.1 生成时已有约束直接引用、只补缺失项 |

**中间件与基础设施子表**（老代码怎么用，新代码就怎么用）：

| 中间件 | 扫什么 |
|---|---|
| 数据库 | MySQL/PG/Oracle：版本、库名、账号、字符集、连接池（HikariCP/Druid） |
| 消息队列 | RabbitMQ/Kafka/RocketMQ：版本、账号、交换机/队列/路由键命名、ACK 方式、消费组 |
| 缓存 | Redis：版本、密码、key 前缀规范、序列化方式；本地缓存（Caffeine/Guava） |
| 定时任务 | Quartz/XXL-Job/@Scheduled：调度方式、任务表、防重入方式 |
| 文件存储 | 本地磁盘/MinIO/OSS：上传目录、访问方式 |
| 搜索引擎 | Elasticsearch：版本、索引命名 |
| 接口文档 | Apifox/Swagger：联调方式、文档维护位置 |
| 日志 | Logback/Log4j2：日志格式、链路追踪 |
| 配置/注册中心 | Nacos/Consul（Spring Cloud 场景）：配置管理、服务发现 |

> 扫描深度：小项目（<50 文件）全量看；大项目按模块抽样 + grep 兜底——**返回体/命名/中间件配置必须全局确认**，禁止只看一个模块就下结论。

2. **优化决策闸门（强制，用户未明确选择前禁止继续）**——向用户明确展示"是否按规范优化一版存量代码？"，选项可多选，也可跳过：

| 选项 | 含义 | 后续路径 |
|---|---|---|
| java-code-standards | 按 AI 开发代码规范优化存量代码 | 生成存量优化任务，按规范执行（改到哪规范到哪，不追求一步全量） |
| comment-standards | 按 AI 开发注释规范优化存量注释 | 走 comment-standards 存量补注释工作流 |
| database-standards | 按 AI 开发 SQL 规范优化存量表/SQL | 生成存量表结构/SQL 优化任务 |
| 跳过 | 不优化存量代码 | 2.1 走存量适配模式（对齐老项目约定；**注释/日志不豁免**——新代码仍全量注释 + 日志完善） |

- **这是 0.5 的强制闸门**：向人展示选项并**等待明确选择，未选择前不得进入 1.1**；选择结果记入扫描结论"优化决策"章节
- 选择优化 → 先按所选规范执行存量优化（优化期间可暂停新需求开发），完成后更新扫描结论，再进入 1.1
- 选择跳过 → 记录"跳过优化"，2.1 必须按**存量适配模式**生成约束（对齐老项目约定；**注释/日志不豁免**——新代码仍全量注释 + 日志完善）

3. **产出扫描结论并落盘**：`docs/0.5-存量代码扫描.md`（参考模板 `templates/0.5-存量代码扫描.md`）——老项目约定基线（包/返回体/命名/数据访问/中间件/可复用组件）+ 项目级约束文件识别（有无 + 覆盖范围）+ 优化决策（优化项 / 跳过）。该文件是项目级基线，跨模块共享；2.1 生成约束时引用它——**老项目有约束文件：已有约束引用不复制、只补缺失项；无约束文件：全部约定写入 2.1**。

## 输出

`docs/0.5-存量代码扫描.md`（参考模板 `templates/0.5-存量代码扫描.md`）

## 完成标准

- [ ] 包结构与分层/返回体/命名风格/数据访问层/接口与错误码/认证鉴权/中间件/工程环境/测试基线/项目级约束文件十项全部扫描并有证据（文件路径）
- [ ] 返回体、命名、中间件配置已全局确认（grep 兜底，非抽样）
- [ ] **优化决策闸门已执行**：人已明确选择（优化哪几项 / 跳过），未选择不进入下一步
- [ ] 选择优化 → 存量优化已按所选规范执行或已明确排期
- [ ] 扫描结论已落盘 `docs/0.5-存量代码扫描.md`（含优化决策记录）
- [ ] 跳过优化 → 已提醒 2.1 走存量适配模式（新代码对齐老项目约定，仅本次开发流程生效）
