# ai-dev-workflow 完整流程执行细则（0.0 / 0.5 / 0.8 + 1.1~5.3）

> 本文件是 `SKILL.md` 的**下挂正文**：走**完整流程**（按流程开发模块 / 从需求到代码）时**必须读全文**。
> **轻量模式（写个接口）与 quick-change 增量轻量不需要读本文件**——它们只需 SKILL.md 的「方式三」与「硬性约束」。
> 拆分理由：SKILL.md 是触发即整篇进上下文的入口文件，把完整流程正文下挂可让高频的轻量场景少付约 40% 常驻 token。

> [!IMPORTANT] 本文件与 SKILL.md 冲突时：**硬性约束 / 交互闸门口径以 SKILL.md 为准，执行细节以本文件为准**。

| 流程步骤 | 必须加载的规范 skill | 覆盖内容 |

| 2.1 `/constraints` | **build-standards**（标准模式，含走 0.5 选优化）；存量适配模式 → **`templates/2.1-项目约束-存量适配.md`**（约束来源 = 0.5 扫描结论，非规范 skill） | 技术架构选型、依赖/版本管理、多模块结构；存量模式 = 老项目约定（包/返回体/命名/中间件） |

| 4.1 `/task-breakdown` | **database-standards** | Mapper XML 触发条件（简单查询禁 XML） |
| 5.1 `/implement` | **java-code-standards**（必读）+ **database-standards** + **build-standards** + **comment-standards** | 写代码前先加载：Java → java-code-standards（命名/分层/注释引用）+ comment-standards（注释）；SQL/MyBatis-Plus → database-standards；pom/依赖 → build-standards。编码按方案实现，完成即停，不自行执行全量核对 |
| 5.2 `/check-standards` | **check-standards** skill | **强制独立节点，始终执行**；先矫正产物命名/路径 → 跑 `scripts/check_standards.py` + 全项核对（无 Python 回退 grep/ast-grep）；**轻量/增量走收窄清单（见方式三），仍执行不豁免** |

用斜杠命令按步骤执行，每步可独立触发、独立检查：

> **模板编号 ≠ 产物编号**：`templates/` 下模板的 `3.0/3.1/3.2/3.3/3.4` 等是**模板库索引号**（每类模板一份）；产物文件名里的 `3.<功能项序号>.1/.2` 等是**产物编号**（功能项 × 子产物序号）。两者体系不同、不要求对等（如接口清单模板是 `3.4-…`，产物是 `3.<功能项序号>.2-…`）——产物的规范文件名以上面规则为准。

> **docs 模块目录命名**：`<模块名>V<版本号>-<YYYYMMDDHHMMSS>`——模块名 + V 开头版本号（**从 PRD/需求文档获取**，如 V1.2.0）+ 连字符 + 功能清单生成时间戳（YYYYMMDDHHMMSS）。例：`docs/订单模块V1.2.0-20260824103000/`。目录在 1.1 功能清单步骤创建（`/feature-list` 从需求文档读取版本号），后续步骤产物（含 2.1 项目约束）全部落入该目录，跨版本开发互不覆盖。

## 中间产物确认闸门（强制，所有步骤适用）

**每一步产出中间产物后，AI 必须停下来，等人在场确认，禁止连续执行到下一步。**

确认流程（每步通用）：

```
1. 该步产物落盘（md/代码）
2. AI 对照该步"完成标准"逐项自检，向人展示：
   - 产物位置（文件路径）
   - 完成标准核对结果（每项 ✅/❌）
   - 关键内容摘要（如功能清单表格、约束条目、方案要点、需求覆盖结论）
3. 人检查产物 → 确认通过 / 提出修改意见
4. 人确认后 → 才进入下一步；有修改意见 → AI 修改后重新展示确认
```

- **每步一个闸门，禁止跨步**：0.5 确认后才能 1.1；0.8 确认后才能 1.1（迭代场景）；1.1 确认后才能 1.2；1.2 确认后才能 1.3；1.3 确认后才能 2.1……依次类推
- 关键闸门（必须人明确确认，不能默认通过）：
  - **0.5 优化决策**：是否按规范优化存量代码——人明确选择（优化哪几项 / 跳过）后才可进入 1.1
  - **0.6 可行性评估结论（可选前置）**：🟢/🟡/🔴 **人拍板后才可进入 1.1**（🟡 卡片逐条定案后放行；人选择跳过评估则无本闸门）
  - **0.8 变更影响分析（迭代场景强制）**：历史产物定位 + 变更映射 + 产物同步计划——**人确认后才进入 1.1，未确认不动任何代码**
  - **0.9 需求构成清单（可选前置）**：模块边界 + 各模块需求 md（含来源段落追踪）——**人确认后才进入 1.1**
  - **1.1 功能清单**：类型/验收标准/依赖是否齐全；**需求分档（A/B/C）+ 验收基线已确认**；迭代场景 0.8 变更映射已全部落实
  - **1.2 需求质量核对（强制独立节点）**：原文回读无遗漏/误读 + 矛盾项无静默选边 + 术语↔码值对齐——**未确认不得进入 1.3**
  - **1.3 澄清问题清单**：所有**未勾选（🔲）卡片**必须人逐条勾选定案（含 req-gate 交来的矛盾/术语 🔲 项、🔴 阻塞项；逐步勾选式卡片模板）
  - **2.1 项目约束**：技术选型与硬规则是否符合预期
  - **3.x 技术方案**：接口/DDL/验收场景无"待定"
  - **4.1 任务拆解**：任务粒度 + 每任务完成标志可独立判定
  - **5.1 编码结果**：按方案实现完成 + 代码抽查
  - **5.2 规范核对报告（强制独立节点、始终执行）**：全 ✅ 或 ❌ 已补齐（报告落盘 `5.2.<功能项序号>-<功能名>-规范核对报告.md`）——**由用户确认通过**；5.2 不再作为"缺报告即拒绝 5.3"的硬前置
  - **5.3 需求覆盖报告（用户可选、默认不执行）**：**开工前先问（附【AI 推荐】）**；选择执行 → 逐需求点 `file:line` 证据或明确缺口、语义项禁 ✅、Listener/Job 默认"未验收"不阻塞；跳过 → 不落盘，模块进度标 `⏭ 已跳过（经确认）`
- 人未确认前，AI 不得继续下一步（这是"防跑偏"的第零道闸门：人有权在任意一步叫停修正）


## 五步流程

> [!IMPORTANT] 执行任一步骤前，必须先读对应命令文件
> 下表只回答"何时走 + 哪些硬点不可协商"。**每步的输入 / 动作 / 输出 / 完成标准只维护在本 skill 的 `commands/` 目录**（如 `commands/design.md`、`commands/check-standards.md`）——进该步前用 read_file 读该文件全文，**禁止只凭本表摘要执行**（摘要漏掉的细节会直接导致产物不合规）。

| 步骤 | 命令 | 何时走 | 不可协商的硬点 |
