# AI 开发完整流程（需求 → 上线）

## 闸门 · 入口分诊（先于 0.0 / 0.5 / 1.1 与全部章节）

**任何改动类请求进来，先做这一步，再决定要不要读本文其余章节。** 判为「小」→ 立即转 quick-change-workflow，本文其余章节一律不展开（不跑 0.5、不产 1.1/3.x、不拆任务）；判为「大」→ 往下走完整流程。

### 判据（量化，不靠感觉）

**小 → quick-change-workflow**（下列**全部**满足）

- 已有模块内，预计改动 **≤ 3 个文件**、单入口（1 个接口 / 1 个 Job / 1 个 Listener）
- **不新增表、不改表结构**；不改契约的破坏性部分（**加字段可以；删字段 / 改签名 / 改语义不行**）
- 不动状态机、权限模型、主链流程；缺陷有可复现路径

**大 → 本流程**（任一命中）

- 全新模块 / 新表 / 新状态机 / 跨模块契约破坏性变更 / 需升版本目录 / 需重走 1.1~5.3 / 有需求文档且要落全套产物

**判不清 → 必须问程序员，禁止自行推定**

- 一次列清两条路（按小改动走 quick-change／按完整流程走）+ **【AI 推荐】** + 理由（引上面哪条门槛满足或不满足），等用户答复后再动手
- **禁止**"先按大的跑反正不会错"，**禁止**"先按小的改，不行再说"，**禁止**"我先改着看" —— 两种默认都是替用户拍板，且事后返工成本更高

### 留痕（每轮必写，判错才能被纠正）

回答第一句固定写判档结论：

> 判档：小 → quick-change（依据：单接口 + 不动表 + 不动契约）

判档行缺失 = 入场未完成；用户看到依据不对可直接改判，AI 立即改道、不辩解。

> 与 quick-change-workflow 的分工：**改动类请求的判档优先权在本节**。quick-change 的"已指明文件/改法 → 短路"只在**判档确认属小改动之后**才生效，不得用来跳过本节。

## 核心原则

**不跑偏**：让 AI 生成规范、可验证、可维护的代码。五道防线：

1. **类型化模板** — 每种产物格式固定（Controller/Listener/Job），AI 没有发挥空间
2. **验收场景前置** — 方案阶段写死"怎么算对"，作为 5.3 需求覆盖核对基准（不再翻译成测试）
3. **约束硬规则** — 项目约束是"能检查对错"的规则，AI 逐条对照
4. **角色分离** — 需求覆盖报告由独立步骤生成，不由实现代码的 AI 自评（防假成功）
5. **收敛兜底** — 实现后按类型逐条核对，防规格漂移

## 0.0 项目/工程初始化（脚手架，从零生成项目必做）

**适用范围**：从零生成/初始化 Spring Boot 工程（含 AI 一次生成整个项目）。**在既有项目里迭代新需求则跳过本节**：老代码基础上迭代 → 先走 0.5 存量代码扫描与约束适配；**已接入规范体系的项目**（项目级约束文件已按本流程 2.1 生成并固化，如 AGENTS.md 含本流程约束）里开发新模块 → 直接走 1.1。**判定不了项目是否已接入规范 → 一律按老项目走 0.5，不自行猜测**（宁可多扫一次，不可漏掉优化决策）。

**为什么必须有这一步**：流程 1.1~5.3 假设"项目已存在"，但一次生成整个项目时，工程骨架缺基础设施会导致**启动即炸**。历史踩坑（真实事故）：

| 缺失/错误 | 启动/运行现象 |
|---|---|
| 只有单个 application.yml，无环境拆分 | dev 配置带到生产，连错库 |
| datasource 只配 url/username/password，无 HikariCP 池参数 | 高并发连接打满，难排查 |
| JDBC URL 写 `characterEncoding=utf8mb4` | `Unsupported character encoding 'utf8mb4'` 启动失败 |
| JDBC URL 端口默认 3306，实际环境非 3306（NAT/容器映射） | `Access denied for user 'xxx'@'localhost'` 连接被拒 |
| 实体 `@TableField(fill=...)` 但项目无 MetaObjectHandler | 一插即炸：`Column 'create_time' cannot be null` |
| 库/表沿用旧 schema，与代码 Entity 不匹配 | `Unknown column 'real_name' in 'field list'` |
| MySQL 8 配了 5.1 旧驱动 | 字符集/时区/加密协议一串兼容问题 |

**执行**：按 `/0.0-项目初始化` 命令执行——**11 项脚手架硬检查（配置四件套/HikariCP/字符集/端口/MP 插件/MetaObjectHandler/建表 utf8mb4/驱动 8.x/logback/接口文档/Spotless）+ 启动验证**，缺一项即不合格。**11 项完整清单只维护在 `commands/0.0-项目初始化.md`**（执行前必读，不凭记忆核对）；规范出处：配置文件/连接池/字符集 → java-code-standards `01-java/application-config-standards.md`，表/schema → database-standards `standards/table-design-standards.md`，依赖 → build-standards `standards/dependency-standards.md`。

> [!NOTE] 0.0 与 2.1 选型衔接
> 脚手架默认选型（Logback + springdoc-openapi）仅作**工程基线**；第 ② 步 2.1 会**人确认工具选型**（日志框架 Logback/Log4j2、接口文档工具 springdoc/knife4j/Apifox）。2.1 确认的选型与脚手架默认不一致时 → **按 2.1 调整**（如确认 Log4j2 则排除 logback 并配 log4j2.xml；确认 Apifox 纯在线文档则按老约定），0.0 默认值不约束 2.1 决策。

## 0.5 存量代码扫描与约束适配（老代码基础上迭代新需求必做）

**适用范围**：在已有代码库（老项目/历史项目/他人维护项目）上迭代新需求，或在不了解现状的既有工程里开发。**从零新项目跳过本节**。核心思想：**先摸清老项目约定，再决定新代码怎么对齐**——新需求代码风格与老项目一致，不被规范 skill 的标准答案带偏。

**为什么必须有这一步**：老项目 ≠ 新项目。老项目有自己的包结构、返回体（如 `R`/`Response`）、命名风格、中间件版本与账号。若新代码直接按规范 skill 的"标准答案"写，会与老项目风格冲突、无法融入。先扫描把"老项目约定"固化成约束文件，AI 编码时才有据可依。

**执行流程（命令 `/legacy-scan`，扫描只读不改代码）**：

1. **先扫描老代码**：按 **10 项约定维度**逐项记录证据（文件路径/配置项）——包结构与分层 / 返回体与公共组件 / 命名风格 / 数据访问层约定 / 接口与错误码 / 认证鉴权 / 中间件与基础设施 / 工程与环境 / 验收能力 / 项目级约束文件。**各项采集方式（grep 什么、读哪些文件）与中间件子表只维护在 `commands/legacy-scan.md`**，执行前必读；深度：小项目全量看，大项目抽样 2-3 个核心模块 + grep 兜底（**返回体/命名/中间件配置必须全局确认**）

2. **优化决策闸门（强制，用户未明确选择前禁止进入 1.1）**——向用户明确展示"是否按规范优化一版存量代码？"，选项可多选，也可跳过：

| 选项 | 含义 | 后续路径 |
|---|---|---|
| `java-code-standards` | 按 AI 开发代码规范优化存量代码 | 生成存量优化任务 → 按规范执行（改到哪规范到哪，不追求一步全量）→ 更新扫描结论 → 进入 1.1 |
| `comment-standards` | 按 AI 开发注释规范优化存量注释 | 走存量补注释工作流 → 完成后进入 1.1 |
| `database-standards` | 按 AI 开发 SQL 规范优化存量表/SQL | 生成存量表结构/SQL 优化任务 → 执行 → 进入 1.1 |
| `跳过` | 不优化存量代码，只保证新需求代码与老项目一致 | 2.1 走**存量适配模式**（对齐老项目约定） |

**这是 0.5 的强制闸门**（同下方"中间产物确认闸门"）：向人展示选项并等待明确选择，**未选择前不得进入 1.1**；选择结果记入扫描结论（0.5-存量代码扫描.md"优化决策"章节）。

3. **产出扫描结论落盘**：`docs/0.5-存量代码扫描.md`（老项目约定基线 + 优化决策），2.1 生成约束时引用

> [!IMPORTANT] 存量约束口径
> **跳过优化 ≠ 新代码放飞**。用户选择跳过优化后，2.1 必须走**存量适配模式**：新需求代码按老项目约定生成约束（包结构/返回体/命名/中间件对齐老代码），该约束是硬规则，AI 编码时逐条对照。规范 skill 仅在老项目无对应约定时才作为兜底。
> **注释与日志不豁免**：老项目存量代码注释稀疏、日志不完善**不是新代码豁免的理由**——本次新增/修改的代码**必须全量注释**（comment-standards：所有类/方法含 private/抽取方法）**且方法级日志完善**（java-code-standards 日志规范 §1.6：每个业务方法方法体 ≥1 条 INFO/WARN/ERROR 日志（debug 不算）+ 入口入参耗时/关键节点 INFO/异常 ERROR 带堆栈），见 2.1 存量适配模板"注释规范/日志规范"章节。

## 开发场景判定（流程入口，先判定再走流程）

### 第一步 · 增量轻量识别（判据在文首「闸门 · 入口分诊」，本节只留执行动作）

- **判为「小」** → 一句识别提示后转 **quick-change-workflow skill（`/quick-change`）**：产物定位 + 轻量产物同步 + 最小改动 + `/check-standards` 兜底，**不展开 1.1~5.3**。判据、门槛、判不清时的问法**只在文首闸门维护，本节不复述**（避免两处分叉）。
- **判为「大」** → 进入下面「第二步 · 项目现状判定」按完整流程走。
- **判不清** → 按文首闸门第 3 条：列两条路 + **【AI 推荐】** + 理由，等用户确认后执行；**禁止自行推定方向**（不得默认"先按大的跑"或"先按小的改"）。

> 设计意图：简单单表 / 小改动若强行走 1.1~5.3 会显著拉长耗时、多烧 token；入口先分诊，把小增量导到轻量通道，把拿不准的交回程序员判断。

### 第二步 · 项目现状判定

走完整流程前，**再确认项目现状（由人确认，AI 不得自行跳过判定）**：

| 场景 | 判定依据 | 走哪条路 |
|---|---|---|
| 从零新项目 | 项目尚不存在，从零生成工程 | **0.0 项目初始化** → 1.1 |
| 老代码/既有项目迭代 | 项目已存在，且**未接入本流程规范**（无项目级约束文件，或约束文件非本流程 2.1 产物） | **0.5 存量代码扫描与约束适配**——**进入即弹"是否按规范优化存量代码"决策闸门** → 1.1 |
| 已接入规范项目新模块 | 项目级约束文件已按本流程 2.1 生成并固化（AGENTS.md 等含本流程约束） | 1.1 直接起 |
| **同模块已有产物迭代（改逻辑 / 新版本）** | 项目已接入规范，且 **`docs/` 下已存在该模块历史产物目录**（`<模块名>V<版本>-<时间戳>/`，含 1.1 功能清单/3.x 方案） | **0.8 迭代变更影响分析（/change-impact）**——**先定位旧产物、变更映射、产物同步计划，人确认后才从源头 1.1 同步** → 1.1 |

> [!WARNING] 判定兜底
> **判定不了项目是否已接入规范 → 一律按老项目走 0.5**，不自行猜测（宁可多扫一次，不可漏掉优化决策）。"是否按规范优化存量代码"的提醒是流程的强制环节，任何情况下不得被静默跳过。

## Git 基线纪律（可选，推荐；老项目无 git / 项目无构建可跳过并注明）

git 是流程的"干净起点 + 可追溯收尾"的底座。使用 git 的项目建议遵守：

1. **动工前**：`git status` 确认工作区干净；从主分支新建独立分支（`git switch -c feature/<模块>`），**不在 main/主分支上直接开发**；跑一次现有构建确认"起点能构建通过"（无构建 → 记"无基线"）；
2. **开发中**：每个任务（4.1 任务项）完成后独立提交，commit message = 任务 ID + 描述；不混提交、不提交半成品；
3. **收尾**：向用户展示工作区状态与改动摘要，由用户决定 **merge / 开 PR / 保留 / 丢弃**；**不自动 merge、不代用户 push**；老项目无 git → 跳过并在进度文件中注明原因。

## 两种使用方式

### 完整流程的执行细节（下挂在 `references/完整流程.md`，必读）

完整流程（0.0 / 0.5 / 0.8 → 1.1~5.3）的执行细节**不在本文件**，按需读 **`references/完整流程.md`**：

| 块 | 内容 |
|---|---|
| ① 配套规范 skill 触发矩阵 | 每个步骤必须加载哪个规范 skill |
| ② 方式一命令表 | 分步执行的 19 条命令 + 何时用 |
| ③ 落盘规则 | 所有产物路径 + 命名规则（去任务 ID 前缀）+ 模块目录命名 |
| ④ 中间产物确认闸门 | 13 个强制人确认点 + 每步自检展示口径 |
| ⑤ 五步流程表 | 每步「何时走 + 不可协商的硬点」 |

> [!IMPORTANT] **走完整流程前必须先读该文件全文**，禁止只凭本表摘要执行（摘要漏掉的细节会直接导致产物不合规）。
> 两条不变量即使不读该文件也成立：① 完整流程**每步产物必须人确认后才能进入下一步**；② 产物路径与命名以「落盘规则」为准（去 T0xx 前缀、按功能项序号）。

### 方式二：一句话全流程

用户说"按流程开发 XX 模块"时，**先执行上方"开发场景判定"**（新项目→0.0；老代码迭代→0.5 含优化决策闸门；已接入规范新模块→1.1；**同模块已有产物迭代→0.8 变更影响分析**），**再读 `references/完整流程.md` 后按流程顺序执行**（命令表 / 落盘 / 13 个确认闸门 / 五步流程硬点均在该文件）。**命中可行性风险信号（未用过外部系统/选型争议/成本不清新方向）→ 人确认是否先 0.6 `/feasibility`**（一页速评 go/需澄清/kill，人拍板）。**需求跨多 Java 模块 / 超大 / 混杂非 Java 服务端内容（任一）→ 先执行 0.9 `/req-intake`**（非 Java 部分直接忽略，人确认后各模块才进入 1.1）；单模块纯 Java → 直接 1.1。**每步产物必须给人确认后才能进入下一步**（确认点清单见 `references/完整流程.md`；1.1 后必须过 1.2 `/req-gate` 需求质量核对闸门才可进 1.3）。中途用户可要求跳到任一 `/命令`。

### 方式三：轻量模式（写个接口 / 改个功能，非完整模块开发）

当用户只是"写个 XX 接口 / 实现 XX 功能 / 改段代码"，而非完整模块开发时，**不强制走 1.1~4.1 重步骤**，直接：

1. **加载规范**（写码前必做）：Java → java-code-standards + comment-standards；SQL → database-standards；pom → build-standards
2. **写码**：全量注释 + 全量日志
3. **收尾兜底**（硬性，**不豁免**）：加载 **check-standards** skill 逐项核对，未执行到位项提示用户确认是否补齐
4. **5.3 需求覆盖核对：默认不执行**，由用户选择（询问口径见下表「五步流程」5.3 行）

#### 轻量 / 增量场景的 5.2 收窄范围（仍执行，不降级为"不核"）

轻量模式与 quick-change 增量轻量**不跑 57 项全量人工判定**，按下列收敛清单执行——**脚本照跑（本地零 token），模型只人工判这几项**：

| | 收窄项 | 为何保留 |
|---|---|---|
| 1 | 方法级注释 + 日志全覆盖（含 private/抽取方法） | 用户定的硬要求，唯一兜底 |
| 2 | 分层边界 / Entity 不外泄 / 统一返回体 | 改错即污染 |
| 3 | SQL 在 XML + SQL 注入 + UPDATE/DELETE 带 WHERE + 分页上限 | 数据安全 |
| 4 | 事务 rollbackFor / 敏感信息进日志 | 一炸就是线上事故 |

其余项（命名细节、格式、场景化横切等）由**脚本结果直接引用**，不逐条人工展开；**脚本报 `manual/warn` 且落在上表 4 类之外的**→ 列进待确认清单让用户选（不静默丢弃）。**完整模块开发（走 1.1~5.3）仍按 57 项全核。**

> 5.3 需求覆盖核对在轻量/增量场景**默认不执行**（逐需求点回读代码是模型 token 大头，而增量场景的需求点已由 1.1 补项 + 回归证据覆盖）；用户主动要求时照常执行。

> 轻量模式只是跳过"功能清单/技术方案/拆任务"这些中间产物，**代码质量三条硬要求（全量注释、全量日志、check-standards 兜底）不打折**。老项目迭代同样先按上方"开发场景判定"走 0.5 存量扫描（至少对齐老项目包结构/返回体/命名/中间件），再走轻量模式。
>
> [!CAUTION] 轻量模式 vs 增量轻量 vs 0.8 的边界
> **轻量模式仅适用于真·零散新增**（一个独立接口 / 工具，该模块 docs/ 无既有产物需同步）。
> **已有模块上的小增量（修 bug / 优化 / 补一个小功能点、加字段/小逻辑）→ 转 quick-change-workflow（`/quick-change`）增量轻量流程**（产物定位 + 轻量产物同步 + 最小改动 + /check-standards 兜底），**不在这里直接写码、也不铺 0.8 全套**。
> **需要升版本目录 / 跨模块 / 重走 1.1~5.3 主链的迭代 → 先 0.8 `/change-impact`**（定位旧产物 + 变更映射 + 产物同步计划，人确认）→ 从源头 1.1 同步。
> 拿不准 → **问用户**：列「按小改动走 quick-change 增量轻量」与「按大改动走 0.8」两条路 + **【AI 推荐】** + 理由，等答复再执行；**禁止自行按任一侧推定**。同时**禁止拿"轻量模式"当绕过产物同步的借口**。

## 产物进度与接续断点（/progress）

每个模块版本目录维护一份 `通用-模块进度与断点.md`（`docs/<模块名>V<版本号>-<时间戳>/通用-模块进度与断点.md`），作为该模块的**唯一进度事实**：

- 在 1.1 `/feature-list` 创建模块版本目录时**同步创建**（模板 `templates/通用-模块进度与断点.md`）；
- 每个中间产物**经人确认后同步更新**对应步骤行状态（只允许 `✅ 已确认` / `🔲 待办` / `⏸ 当前断点` / `⏭ 已跳过（经确认）`（仅用于可选节点 5.3），禁止另造状态值）；
- **跨会话 / 换人接手必须先 `/progress`**：读 通用-模块进度与断点.md → 报告断点 → 从断点续跑，**禁止从 1.1 重跑**（流程产物 + 人工闸门可被机器化接续，但每次续跑仍遵守对应步骤的确认闸门）。
- **自然语言续跑入口**：用户说「继续订单模块」「继续订单模块的需求」「继续上次中断的任务」「接着上次」等 → 一律按本机制处理：AI 收到此类意图即执行 /progress 逻辑（定位模块 → 读 通用-模块进度与断点.md → 报告断点 → 从断点续跑）。

## 硬性约束（写入编码 Agent 提示词，不可协商）

```
1. 严格按 Phase 顺序：先数据层 → 再公共组件（Phase 0.5，**任务拆解内的公共组件阶段，与流程步骤 0.5 存量扫描无关**）→ 再业务 → 再接口/消费/调度
2. 必须遵守《项目约束》的全部规则（逐条对照，含"注释规范"与"公共组件规范"章节）
3. **生成的代码必须遵守约束文件约定**：写任何代码前先对照 `2.1-项目约束.md`。标准模式遵守规范 skill 约定（Java → java-code-standards + comment-standards；SQL/表/MyBatis-Plus → database-standards；pom/依赖 → build-standards）；**存量适配模式遵守老项目约定（包结构/返回体/命名/中间件对齐老代码），规范 skill 仅在老项目无对应约定时兜底**。生成物不符合约束即不合格、需返工
4. 每个任务完成后独立提交（commit message = 任务 ID + 描述）
5. 不实现任务拆解.md 之外的东西（不做"顺手优化"）；Phase 0.5 列出的公共组件必须实现并被复用点调用/继承。编码中发现设计外的重复逻辑：不擅自抽取，标注 `// TODO(收敛)` 由需求覆盖阶段统一处理
6. 写代码时同 pass 生成注释（内容从技术方案派生，禁止事后补/编造），遵守注释规范（见 comment-standards skill）——**全量注释，禁止大段代码无注释**（存量适配模式同样适用，不因老项目注释稀疏豁免）
7. 写代码时同步生成日志（遵守日志规范，见 java-code-standards `00-common/04-logging-standards.md` §1.6 方法级日志覆盖）——全类 @Slf4j、**每个业务方法（public + private 抽取方法）方法体内 ≥1 条 INFO/WARN/ERROR 日志（debug 不算）**（入口记入参摘要+耗时、关键节点 INFO、异常 ERROR 带堆栈；大段逻辑 ≥10 行无 INFO/WARN/ERROR = 不合格；存量适配模式同样适用，不因老项目日志稀疏豁免）；收尾阶段核对注释、日志、权限、事务、幂等、防重入
8. **与简洁类 skill（如 ponytail）共存：先满足本流程硬规则，再追求最简实现**——本流程的分层/注释/中间产物是用户明确要求的硬规则，简洁类 skill 不得砍减；其极简原则仅在规范未指定的地方生效（见下方「与简洁类 skill 共存规则」）
9. **5.2 规范核对是强制独立节点（编码 Agent 不自行执行全量核对）**：5.1 编码完成后停下，进入 `/check-standards`（加载 **check-standards** skill：**优先跑 `scripts/check_standards.py` 机械扫描，无 Python 回退标准 grep/ast-grep 指令**）独立核对**全部核对项（无级别之分，含方法级注释/日志全覆盖——private/抽取方法逐个查）**，每项**附实际执行证据（文件:行号）**；**所有未执行到位项（无级别之分）→ 一起向用户展示证据、确认"是否按规范补齐" → 用户确认后才执行补齐** → 重跑该项 + 新证据 → 仍 ❌ → 升级人工核对；产物 `5.2.<功能项序号>-<功能名>-规范核对报告.md` 落盘并获用户确认后，**再询问用户是否执行 5.3 `/accept`（需求覆盖核对为用户可选节点，默认不执行；5.3 不再因缺 5.2 报告而拒绝）**。禁止"没做就声称做了"、禁止编码 Agent 自评通过、禁止把任何 ❌ 当"不重要"跳过
```

## 与简洁类 skill 共存规则（如 ponytail）

同时加载本流程 skill 与简洁类 skill（ponytail：YAGNI / stdlib 优先 / 最少文件 / 最短 diff）时，按以下优先级协调，禁止互相覆盖：

1. **本流程产物是用户明确要求的硬规则**：分层（Controller/Service/Impl/Mapper/Entity/DTO/VO）、注释规范（comment-standards）、中间产物 md（功能清单/方案/需求覆盖报告）——简洁类 skill 的"最短 diff / 解释不超 3 行 / YAGNI applies to tests"**不适用于这些显式要求的产物**。ponytail 自身的"Never simplify away: anything explicitly requested"条款与之天然兼容
2. **优先级：规范硬规则 > 极简优先 > 默认行为**——先满足规范，再追求最小实现；规范未指定的地方（如公共组件识别、依赖选型、实现方式）才应用简洁类 skill 的极简原则
3. **简洁类 skill 的适用边界（在规范内生效）**：
   - 不重复造轮子：规范已约束的公共组件/工具类直接复用，不重写
   - 不引入多余依赖：已有依赖能解决的不新增（对齐 build-standards 依赖规范）
   - 不写规范未要求的抽象：无单一实现接口、无多余配置项
   - 公共组件识别更保守：第 2 个使用点才抽公共的规则不变，但候选更严格
4. **流程产物不受"解释超 3 行"限制**：功能清单/技术方案/需求覆盖报告是用户显式请求的文档，给出完整内容

> 注意：存量适配模式（老项目跳过优化）同样适用本规则——对齐老项目约定仍是硬约束，简洁类 skill 只在老项目无约定处生效。

## 常见错误

| 错误 | 修正 |
|---|---|
| 跳过 3.x 直接让 AI 写代码 | 方案有歧义，后面全跑偏。3.x 是质量闸门，宁可多花时间 |
| 约束写成"尽量/建议" | 无法检查 = 无效约束。必须是能判对错的规则 |
| 验收场景只写正常路径 | 非法/边界场景缺失 = 需求覆盖有洞。三态都要有 |
| 实现完不核对方案 | 规格漂移悄悄发生。验收核对应是最后一关 |
| 让 AI 编码时"顺手"抽公共类 | 会跑偏（改任务外代码）。公共组件必须方案期识别（3.x 架构自检）+ 拆入 Phase 0.5，编码只实现不复抽 |
| 委派断链后直接编码却不加载规范 skill | 生成物不符合规范、验收返工。规范 skill 加载是写码前第一步，见硬性约束第 3 条 |
| 澄清阶段没确认入口/复杂度 | 第零段判定靠 AI 猜，方案四段选错、全链跑偏。入口形态/业务复杂度/状态机归属必须在 1.3 澄清盘问并由人确认 |
| 需求文档有矛盾/术语不齐就直接拆功能项 | 需求点拆错（误读/收窄/静默选边）覆盖核对照样全绿。1.1 产物确认后必须过 1.2 `/req-gate`（原文回读 + 矛盾扫描 + 术语↔码值对齐），未过闸不得进入 1.3 |
| 同模块改逻辑/迭代不溯源旧产物直接改码 | 产物与需求/代码失同步，越改越乱。docs/ 已有该模块历史产物目录 → 先判增量大小：**小增量（修 bug/优化/补一个小功能点）走 quick-change-workflow 增量轻量**（产物定位 + 轻量同步）；**需升版本/跨模块/重走主链的大迭代** → 必须 0.8 `/change-impact`（定位旧产物 + 变更映射 + 产物同步计划，人确认）→ 从源头 1.1 同步 → 才允许写码；**禁止用轻量模式绕过** |
| 把 5.3 需求覆盖报告当"验证通过" | 5.3 是**静态结构核对**，证明需求没漏做，不证明可运行（配置错误/连接失败/旧 jar 过期/库表未初始化它都查不出）。行为验证**按需**用 `test-workflow` 技能（`/gen-test`）真实调用接口，不阻塞主流程 |
| 修 bug 直接盲试改码（猜着改/改跑偏） | 缺陷修复先复现 + assess 根因（证据）→ 最小修复。**Bugfix / 优化 / 小需求补充场景加载 `quick-change-workflow` skill（`/quick-change`）按增量轻量流程**（产物定位 + A/B/C 分层 + 轻量产物同步）；需要升版本/跨模块/重走主链的大变更 → 停、转 0.8（产物同步不豁免），完成统一 `/check-standards` 兜底 |
| 简单单表 / 小改动也铺 1.1~5.3 完整流程 | 费时费 token、几分钟的事拖成长流程。入口先按文首「闸门 · 入口分诊」判档：小增量（缺陷/优化/小需求补充）→ 导 quick-change-workflow 轻量通道；只有全新模块/大迭代才走完整流程；**判不清问用户，不自行推定** |
