# AI 开发完整流程（需求 → 上线）

> **版本**：v3（定稿）
> **适用**：Java 服务端项目（Controller → Service → DAO/Mapper → 数据库；Quartz 定时任务；RabbitMQ 消息）
> **核心思想**：类型化模板（每种产物格式固定）+ 验收场景前置（可翻译成测试）+ 约束硬规则（规范代码）+ 收敛兜底（防规格漂移）
> **目标**：**能生成规范、不跑偏的代码**
> **配套模板**：`skill/ai-dev-workflow/templates/` 目录 24 份空白模板，本文档每步末尾标注对应模板

## 一·五、开发场景判定（流程入口，先判定再走流程）

开始任何开发前，**先确认项目现状（由人确认，AI 不得自行跳过判定）**：

| 场景 | 判定依据 | 走哪条路 |
|---|---|---|
| 从零新项目 | 项目尚不存在，从零生成工程 | **0.0 项目初始化** → 1.1 |
| 老代码/既有项目迭代 | 项目已存在，且未接入本流程规范（无项目级约束文件，或约束文件非本流程 2.1 产物） | **0.5 存量代码扫描与约束适配**——**进入即弹"是否按规范优化存量代码"决策闸门** → 1.1 |
| 已接入规范项目新模块 | 项目级约束文件已按本流程 2.1 生成并固化（AGENTS.md 等含本流程约束） | 1.1 直接起 |
| **同模块已有产物迭代（改逻辑 / 新版本）** | 项目已接入规范，且 **`docs/` 下已存在该模块历史产物目录**（含 1.1/3.x 方案） | **0.8 迭代变更影响分析**（/change-impact）——定位旧产物 → 变更映射 → 产物同步计划，人确认后才从源头 1.1 同步，**禁止直接改码** |

> [!WARNING] 判定兜底
> **判定不了项目是否已接入规范 → 一律按老项目走 0.5**，不自行猜测（宁可多扫一次，不可漏掉优化决策）。"是否按规范优化存量代码"的提醒是流程的强制环节，任何情况下不得被静默跳过。

## 二、第 0 步：项目/工程初始化（脚手架）

**输入**：需求（从零生成整个 Spring Boot 工程时）

**输出**：脚手架检查清单（`templates/0.0-项目初始化.md`），10 项基础设施逐项核对

**对应模板**：`skill/ai-dev-workflow/templates/0.0-项目初始化.md`

**10 项硬检查**（缺一项即不合格，历史事故沉淀）：

| # | 检查项 | 防的坑（真实事故） |
|:---:|:---|:---|
| 1 | 配置文件四件套 `application.yml` + `-dev` + `-qa` + `-online`，profile 激活 `${SPRING_PROFILES_ACTIVE:dev}` | 单文件裸奔，dev 配置带到生产连错库 |
| 2 | HikariCP 显式池参数 | datasource 三件套裸奔，高并发连接打满 |
| 3 | JDBC URL 不写 `characterEncoding=utf8mb4` | `Unsupported character encoding 'utf8mb4'` 启动失败 |
| 4 | JDBC 端口与环境实际一致 + `serverTimezone` | 端口默认 3306 想当然 → `Access denied` 连接被拒 |
| 5 | MyBatis-Plus 插件（分页/乐观锁） | 分页/乐观锁不生效 |
| 6 | MetaObjectHandler（createTime/updateTime 自动填充） | 实体 `@TableField(fill=...)` 无 handler → `Column 'create_time' cannot be null` 一插即炸 |
| 7 | 库表 schema 一致性：显式 utf8mb4 + 按当前 schema 全量重建 | 旧库旧表遗留 → `Unknown column 'xxx' in 'field list'` |
| 8 | MySQL 驱动 Connector/J 8.x（BOM 管理） | 5.1 旧驱动字符集/时区/加密协议坑 |
| 9 | 日志配置：`resources/logback-spring.xml`（控制台 + 滚动文件 + 环境级 level）+ `logging.level` 覆盖 | 日志全打控制台、无文件归档、环境级 level 混乱 |
| 10 | 接口文档依赖：springdoc-openapi（/knife4j）由 BOM 管理，`springdoc.api-docs.enabled` 按环境配置（online 关闭） | 无接口文档依赖，@Tag/@Operation 注解不生效；online 暴露文档 |

**完成标准**：10 项全过 + 启动验证通过（启动无报错、含插入接口调通、各 profile 可切换）。

> 规范出处：java-code-standards `01-java/application-config-standards.md` + `04-templates/`；database-standards `standards/table-design-standards.md`；build-standards `standards/dependency-standards.md`。

## 二·五、第 0.5 步：存量代码扫描与约束适配（老代码迭代新需求必做）

**输入**：项目路径（老代码库）

**输出**：`docs/0.5-存量代码扫描.md`（老项目约定基线 + 优化决策），2.1 生成约束时引用

**对应命令**：`/legacy-scan`；**对应模板**：`skill/ai-dev-workflow/templates/0.5-存量代码扫描.md`

**核心思想**：老代码基础上迭代新需求时，**先摸清老项目约定，再决定新代码怎么对齐**——新需求代码风格与老项目一致，不被规范 skill 的标准答案带偏。

**执行流程**：

1. **先扫描老代码**（提醒并执行，只读不改代码）：
   - 包结构：业务代码放哪个包、分层结构
   - 返回体与公共组件：统一返回类（类名/包位置/字段结构）、分页类、异常处理类、可复用工具类/基类
   - 命名风格：Java 类/变量/方法命名、数据库表/字段命名（驼峰 ↔ 下划线映射）
   - 中间件清单：数据库 / MQ / Redis / JOB 等——版本、账号配置、接入方式、使用规范，与老代码保持一致
   - 项目级约束文件：老项目是否已有约束文件（AGENTS.md / CLAUDE.md / GEMINI.md / README 规范章节等，以实际存在为准，不限于某一文件名）——有则记录覆盖范围，2.1 已有约束直接引用、只补缺失项

2. **优化决策闸门（强制，未选不得继续）——是否按规范优化一版存量代码？**（可多选，也可跳过）
   - `java-code-standards`（代码规范）/ `comment-standards`（注释规范）/ `database-standards`（SQL 规范）
   - `跳过`：不优化存量代码，只保证新需求代码与老项目一致
   - **向人展示选项并等待明确选择，未选择前不得进入 1.1**；选择结果记入扫描结论"优化决策"章节
   - 选择优化 → 先按所选规范执行存量优化，完成后更新扫描结论再进入 1.1

3. **产出扫描结论落盘**：`docs/0.5-存量代码扫描.md`

> [!IMPORTANT] 存量约束口径
> **跳过优化 ≠ 新代码放飞**。用户选择跳过优化后，2.1 必须走**存量适配模式**：新需求代码按老项目约定生成约束（包结构/返回体/命名/中间件对齐老代码），该约束是硬规则，AI 编码时逐条对照。规范 skill 仅在老项目无对应约定时才作为兜底。
> **注释与日志不豁免**：老项目存量代码注释稀疏、日志不完善**不是新代码豁免的理由**——本次新增/修改的代码必须全量注释（comment-standards）且日志完善（java-code-standards 日志规范：入口入参+耗时/关键节点 INFO/异常 ERROR 带堆栈）。

## 二·六、第 0.6 步：需求可行性评估（可选前置）→ `/feasibility`

**适用范围**：需求命中**风险信号**（未用过的外部系统/中间件/SDK、技术选型争议、成本不清的新方向）时，先回答"值不值得做、做不做得动"。**普通需求直接跳过进 1.1**，命中但人选择跳过 → 直接进 1.1。与 1.1 需求分档（描述质量）/ 1.3 澄清（细节歧义）分工不同。

**输出**：`docs/0.6-需求可行性评估.md`（模块版本目录已建则放入其内，未建放 docs/ 根）

**对应模板**：`skill/ai-dev-workflow/templates/0.6-需求可行性评估.md`（一页速评）

**执行**（详见 `/feasibility` 命令）：风险信号判定（命中 → 人确认是否执行）→ 读事实（需求/相关产物/0.5 扫描结论，实查）→ 自查关键未知（读码/查文档）→ 一页速评（风险扫描表 + 关键未知结论 + 体量粗估 + 备选路线 ≥2）→ **结论 🟢 go / 🟡 需澄清 / 🔴 kill，人拍板** → go 后按正常入口进 1.1（超大/跨模块按需先 0.9 `/req-intake`）。

## 二·八、第 0.8 步：迭代变更影响分析（同模块改逻辑 / 迭代必做）

**适用范围**：**同模块已有历史产物目录**（`docs/<模块名>V<版本>-<时间戳>/`）时，改逻辑 / 迭代新需求。这是解决"改逻辑没比对旧需求、没同步产物，越改越乱"的入口闸门。

**为什么必须有这一步**：老需求开发的产物（1.1 功能清单 / 3.x 技术方案 / 接口清单）是后续迭代的比对基准。若改逻辑直接从代码入手、不回源更新产物，产物与需求/代码失同步——下次迭代失去参照，规格漂移悄悄发生。

**输入**：本次变更描述 + 该模块历史产物目录（`ls docs/` 实查，取最新版为基准，旧目录只读不改）

**输出**：`0.8-迭代变更影响分析.md`（历史版本定位 + 变更映射 + 产物同步计划）

**对应命令**：`/change-impact`；**对应模板**：`skill/ai-dev-workflow/templates/0.8-迭代变更影响分析.md`

**执行流程**：

1. **定位历史产物**：列出模块所有版本目录，读取最新版 `1.1-功能清单.md` / `3.<序号>.1-技术方案.md` / `3.<序号>.2-接口清单.md`
2. **变更点映射**：把本次变更拆成变更点，逐点映射旧产物与旧功能项（**新增 / 修改 / 删除**）；落不到旧产物的"新增"也明确记录
3. **产物同步计划**：按 1.1 → 3.x.1 技术方案 → 3.x.2 接口清单 → 4.x → 5.x 顺序列出受影响产物及动作；注明不受影响（继承）项，避免无谓重写
4. **变更影响确认闸门（强制）**：向人展示定位 + 映射 + 计划，**确认后才进入 1.1**（以本分析为输入，继承旧清单按变更点同步），**未确认不动任何代码**

**完成标准**：历史产物已定位（实查目录）；变更映射完整；产物同步计划按流程顺序列出；新版本号已确认、旧目录不动；人确认后才进入 1.1。

> [!WARNING] 轻量模式不豁免
> 同模块已有历史产物时改逻辑 → 一律先走 0.8，**禁止拿"轻量模式（写个接口/改个功能）"当绕过产物同步的借口**。轻量模式仅适用于真·新增的零散接口/工具（无既有产物需同步）。

## 二·九、第 0.9 步：需求入口整形（可选前置）→ `/req-intake`

**适用范围**：需求文档**跨多个 Java 模块 / 体量超大 / 混杂非 Java 服务端内容**（任一命中）。单模块纯 Java 小需求直接跳过进 1.1。

**为什么需要**：超大跨栈需求硬塞给 1.1 会拆漏，且一份巨型功能清单无人能一次确认。先把需求按模块整理成"模块级需求 md"（每份含来源段落追踪，可回溯原始文档），人确认一轮后才进入各模块 1.1——从源头防需求缺失。

**硬规则（非 Java 服务端需求）**：前端/App/小程序/其他语言服务端等**一律直接忽略**——不拆、不列入构成清单、不产文件；仅清单末句注明"已忽略非 Java 服务端部分"。

**执行**（详见 `/req-intake` 命令）：触发判定 → 忽略非 Java 部分 → 识别 Java 模块边界（AI 提议、人拍板）→ 模块清单确认 → 逐模块生成「模块需求 md」（模块范围 + **来源段落追踪** + 验收基线 + 跨模块依赖）→ 推荐开发顺序 → 人确认一轮。

**输出**：`docs/req-intake-<YYYYMMDDHHMMSS>/` 下《需求构成清单与确认.md》+ 每 Java 模块一份《<模块名>-模块需求.md》。

**完成标准**：触发判定明确；非 Java 部分已忽略；模块边界与各模块需求 md **经人确认**；确认后各模块才进入 1.1 `/feature-list`（模块已有历史产物 → 1.1 前先 0.8）。

## 三、第 1 步：需求分析

**输入**：需求文档（模块级）；**迭代模式（docs/ 已有该模块历史产物）→ 先执行 0.8 `/change-impact`**，以 `0.8-迭代变更影响分析.md` 为输入（继承旧 1.1 + 按变更点同步），不是从零重拆

**前置（需求准入，先做）**：需求分档（A 结构化完整 / B 有模糊 / C 碎片化先补文档）+ 验收基线确认（以哪份文档哪个版本为准 + 有无口头补充），结果写入功能清单速览框。

**输出**：功能清单总览文件（**先过滤非 Java 服务端需求** → 列需求点清单 → 拆功能项（标注承接需求点）→ **需求覆盖核对**（每个需求点有承接，无静默消失）→ MVP 切分 → 记录非功能需求）

**对应模板**：`skill/ai-dev-workflow/templates/1.1-功能清单.md`

**表格格式**：

| # | 功能项 | 承接需求点 | 类型 | 优先级 | 依赖 | 验收标准 |
|---|--------|-----------|------|--------|------|----------|
| 1 | 订单创建 | R1, R9 | Controller | P1 | — | POST /order 合法参数 → 返回订单号、订单落库状态 PENDING；非法参数 → 400 + 校验提示 |
| 2 | 订单查询（分页） | R2 | Controller | P1 | — | GET /order/list 分页返回，total 正确 |
| 3 | 订单支付回调 | R5 | Listener | P1 | 依赖 #1 | 收到消息后状态变 PAID，重复消息幂等 |
| 4 | 订单超时关闭 | R6 | Job | P1 | 依赖 #1 | 超 30 分钟未支付自动 CLOSED |

**类型说明**：
- `Controller`：HTTP 接口功能
- `Listener`：MQ 消费者（RabbitMQ）
- `Job`：定时任务（Quartz）
- 其他类型自定，但必须明确触发方式

**粒度规则**：一个功能项 = 一个可独立验收的用户可感知能力（一个端点 / 一个消费逻辑 / 一个 Job / 一组内聚 CRUD）；拆太细（一接口拆多项）或太粗（整模块一项）都不合格（正反例见模板）。

**完成标准**：
- 需求准入已确认（分档 + 基线）
- **需求覆盖核对通过**：每个需求点有承接（功能项 / 已过滤 / 延后），无静默消失
- 每个功能项有：承接需求点 + 类型标签 + 验收标准（**可翻译成契约测试断言**——"输入 → 预期输出/状态变化"，不能写"实现 XX 功能"）
- 粒度符合标准；依赖关系已标注（用于排任务顺序）
- MVP 切分明确（P1 = 本期交付）；模糊需求标"待澄清"；非功能需求已记录
- **产物经人确认后必须过 1.2 需求质量核对（/req-gate）闸门，才可进入 1.3 澄清**

## 三·五、第 1.2 步：需求质量核对（/req-gate）★ 1.3 前的强制闸门

**为什么必须有这一步**：功能清单只证明"需求点被拆成了功能项"，不证明"需求点本身拆对了"——需求点由 AI 拆解，若拆解时误读/收窄范围、或在文档矛盾处静默选边，覆盖核对照样全绿。老项目还常有"需求术语与现有系统枚举/码值对不上"的问题。本闸门对需求文档原文做三道独立核对。

**输入**：1.1 功能清单 + 需求文档原文 + 存量枚举/码值事实源（老项目 → `docs/0.5-存量代码扫描.md`，缺失先 `/legacy-scan`）

**输出**：需求质量核对报告（`1.2-需求质量核对.md`）：需求基线 + ①原文回读核对表 ②跨节矛盾清单 ③术语↔码值对齐表 ④待确认汇总

**对应模板**：`skill/ai-dev-workflow/templates/1.2-需求质量核对.md`

**三道核对**：
1. **原文回读核对**：回读需求文档**逐节**比对——每节有承接；无承接 = 遗漏信号（补项或明确"过滤/延后"）；与原文口径不符 = 误读信号（回退修正）
2. **跨节矛盾扫描**：规格性表述两两交叉核对冲突——**禁止静默选边**，标 🔲 交 1.3 由人裁决
3. **术语↔码值对齐**：需求术语对照存量枚举/码值建映射——对不上标 🔲（是否新增由人裁决，**禁止擅自造新枚举**）

**完成标准**：逐节回读无遗漏/误读残留；矛盾项全部标 🔲；术语对不上已标 🔲；产物经人确认后才进入 1.3（1.2 报告是 1.3 的前置输入）

## 四、第 1.3 步：澄清（Clarify）★ 方案前必做

**输入**：第 1 步的功能清单 + **1.2 需求质量核对产物**（矛盾/术语 🔲 项在此裁决）

**输出**：澄清问题清单（人确认答案）+ 更新后的功能清单（补边界/风险列、完善依赖）

**对应模板**：`skill/ai-dev-workflow/templates/1.3-澄清问题清单.md`

**动作**：逐功能项盘问四类问题，**并逐项裁决 1.2 交来的矛盾/术语 🔲 项**——

| 类型 | 盘问什么 | 示例 |
|---|---|---|
| 歧义（Ambiguity） | 模糊词（"等/相关/尽快"）、未定义字段、不可验证的验收标准 | "订单取消"→ 已发货的能取消吗？ |
| 入口形态与业务复杂度（第零段判定前置） | HTTP 接口 / MQ 消费 / 定时调度 / 无入口（配置/工具）？复合形态？纯 CRUD 转发 / 复杂（多表写、状态流转、算法、并发）？ | "订单支付回调"→ 是 MQ 消费还是 HTTP 回调？幂等靠唯一键还是状态位？ |
| 边界用例（Edge Cases） | 重复提交、并发操作、空值/超长/非法格式、状态流转缺失 | 重复取消请求返回什么？ |
| 依赖（Dependencies） | 功能间依赖、外部系统/第三方、数据依赖 | 订单创建依赖库存服务吗？ |

**完成标准**：
- 每个功能项无未确认的歧义（模糊词已澄清）
- 每个功能项的入口形态（有/无入口、HTTP/MQ/定时）与业务复杂度（简单/复杂）已判定并记录（第零段输入）
- 每个功能项的边界用例已列出（合法/非法/边界三态）
- 依赖完整标注（功能间 + 外部系统）
- **1.2 需求质量核对交来的矛盾/术语 🔲 项已全部裁决**
- 澄清问题清单状态列无"待确认"残留

> 这是防跑偏的第一道闸门：歧义带进技术方案，后面全偏。**宁可在这里多盘问，不要带歧义进入第 3 步。**

## 五、第 2 步：技术架构

**输入**：第 1 步的功能清单

**输出**：技术架构说明 + 项目约束（追加到约束文件；落盘 `docs/<模块名>V<版本号>-<YYYYMMDDHHMMSS>/2.1-项目约束.md`，与 1.1/1.2 等产物同目录）

**对应模板**：`skill/ai-dev-workflow/templates/2.1-项目约束.md`（标准模式）、`skill/ai-dev-workflow/templates/2.1-项目约束-存量适配.md`（存量适配模式）

**两种模式**：

| 模式 | 判定 | 约束来源 |
|---|---|---|
| 标准模式 | 新项目 / 未走 0.5 | 规范 skill（build-standards 等） |
| 标准模式（走 0.5 选优化） | 已走 0.5 且用户选择按规范优化 | 规范 skill（同标准模式）；中间件版本/账号等老项目事实仍对齐（引用 0.5 扫描结论） |
| 存量适配模式 | 已走 0.5 且用户选择跳过存量优化 | **老项目实际约定**（0.5 扫描结论）：包结构/返回体（R/Response）/命名风格/中间件（数据库/MQ/Redis/JOB 版本、账号、接入规范）对齐老代码；规范 skill 仅在无对应约定时兜底 |

**内容**：
- 框架/技术/中间件清单 + 版本号（如 Spring Boot 3.2.x、MyBatis-Plus、Quartz、RabbitMQ；存量适配模式写老项目实际版本）
- 约束写成可强制检查的硬规则，禁止描述性文字：

```markdown
## 项目约束（AI 编码时必须遵守）
1. 统一使用 MyBatis-Plus，禁止原生 JDBC
2. 所有新增接口必须加 @RequiresPermissions 权限注解
3. 数据库操作统一走 Service 层，Controller 禁止直接调用 Mapper
4. 事务：涉及多表写入的方法必须 @Transactional
5. 返回体统一使用 `Response<T>`（code/message/data），禁止直接返回 Map（见 java-code-standards 命名规范）
6. 实体类字段命名统一驼峰，表字段统一下划线
7. 禁止使用 System.out.println，统一 logger
8. Listener 消费必须做幂等处理（唯一键或状态位）
9. Job 必须防重入（分布式锁或状态位）
10. 版本：Spring Boot 3.2.x / MyBatis-Plus 3.5.x / RabbitMQ 3.x
```

**作用**：这是全流程的"宪法"——第 3 步技术方案、第 5 步 AI 编码都必须对照它。

**完成标准**：约束文件可被 AI 直接读取，且每条都是"能检查对错"的规则（不是"尽量""建议"）。

## 六、第 3 步：技术方案

**输入**：第 1 步的功能清单

**输出**：每个功能项一份技术方案 md（3.0 通用骨架 + 类型模板合并），存于 `docs/<模块名>V<版本号>-<YYYYMMDDHHMMSS>/` 目录下（模块名 + V 版本号 + 时间戳，版本号取自需求文档；目录在 1.1 功能清单步骤创建）

**对应模板**：`skill/ai-dev-workflow/templates/3.0-技术方案-通用骨架.md`（所有类型共用，含通用章节 + 类型导航表 + 四段式语法）+ `3.1/3.2/3.3-技术方案-*.md`（类型特有四段内容）

**通用结构**（所有类型都有）：基本信息 → 通用章节（验收场景 / 公共组件识别 / 注释要求 / 数据模型与 SQL / 自检）→ 类型四段（入口定义 / 数据契约 / 核心逻辑 / 关注点）

### 3.1 Controller 技术方案（类型模板，四段式）

类型特有四段（通用章节见 3.0）：入口定义 = 接口清单（汇总表 + 接口明细——**每个 URL 独立小节：入参示例（请求体 JSON）+ 出参示例（成功/失败）**）；数据契约 = 逐字段校验规则；核心逻辑 = Service 映射（纯转发可跳过）；关注点 = 权限注解 + 事务边界（数据模型与 SQL 见通用章节）。

### 3.2 Listener 技术方案（类型模板，四段式）

类型特有四段（通用章节见 3.0）：入口定义 = 监听配置（交换机/队列/路由键/ACK 方式）；数据契约 = 消息体结构（JSON 示例 + 字段约束）；核心逻辑 = 消费主流程（反序列化 → 校验 → 幂等 → 处理 → ACK）；关注点 = 幂等（唯一键 + 重试 + 死信）+ 边界场景（重复/乱序/缺字段）+ 幂等唯一索引 DDL。

### 3.3 Job 技术方案（类型模板，四段式）

类型特有四段（通用章节见 3.0）：入口定义 = 调度配置（cron 表达式）；数据契约 = 无入参（跳过）；核心逻辑 = 执行主流程（防重入 → 筛选 → 逐条处理 → 日志 → 释放锁）；关注点 = 防重入（分布式锁 + 批处理大小）+ 异常告警 + 执行日志表 DDL。

### 3.4 完成标准（Checkpoint，所有类型通用）

- [ ] 技术方案对应一个明确的功能项编号，无遗漏、无多余
- [ ] 第零段定性完成：入口形态（有/无入口）、业务复杂度（简单/复杂）判定明确
- [ ] 跨功能项规则归属已约定（状态机定义在最先触碰的功能项，其他功能项引用）
- [ ] 通用章节完整：验收场景含合法 + 非法 + 边界、公共组件识别完成、注释要求已写明
- [ ] 类型特有内容按四段（入口定义/数据契约/核心逻辑/关注点）取自对应 3.x 模板
- [ ] 复杂业务已写业务规则小节（状态流转 / 计算规则 / 并发处理）
- [ ] 接口/消息/Job 的入参、出参、错误码、校验规则全部明确，无"待定""视情况"；Controller 每个 URL 有独立入参示例（请求体 JSON）+ 出参示例（成功/失败）
- [ ] 数据模型与 SQL 章节完整：模块全量 SQL（建表 DDL 含索引/约束 + 初始化数据 + 查询 SQL）在技术方案内，无独立 sql 目录
- [ ] 权限/事务/幂等/防重入等横切关注点已写明（对照第 2 步约束逐条检查）

### 5.1 AI 执行规则（写进提示词的固定模板）

### 5.2 规范核对（check-standards 兜底闸门）

**Controller 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 接口路径、方法、入参出参 | 技术方案接口清单 | AI 改参数名、漏字段 |
| 校验规则（非空/格式/长度/枚举） | 技术方案入参校验 | 校验缺失或过严 |
| 表名、字段、类型、索引 | 技术方案《数据模型与 SQL》章节 | AI 自创列名 |
| Service 映射 | 技术方案接口清单 | 调错 Service 方法 |
| 权限注解、事务 | 项目约束 #2/#4 | 漏加 @RequiresPermissions |

**Listener 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 队列/路由键/ACK 方式 | 技术方案监听配置 | 队列名写错、忘了手动 ACK |
| 幂等逻辑 | 技术方案幂等方案 | 漏幂等 → 重复消息重复处理 |
| 死信/重试 | 技术方案失败处理 | 漏配置死信队列 |
| 消息体字段校验 | 技术方案消息体结构 | 漏校验必填字段 |

**Job 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| cron/调度注册 | 技术方案调度配置 | cron 写错、漏注册 |
| 防重入锁 | 技术方案并发与锁 | 漏锁 → 并发重复执行 |
| 批处理/超时 | 技术方案执行逻辑 | 一次捞全表 → 长事务 |
| 失败处理/告警 | 技术方案异常与告警 | 单条失败中断全部 |

**注释核对（所有类型必做）**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 公开 API Javadoc 齐全 | 项目约束"注释规范" | 漏写、@param 只重复参数名 |
| 无逐行翻译式注释 | 项目约束"注释规范" | `// 价格乘以数量` 类废话 |
| 复杂逻辑有 // WHY: | 项目约束"注释规范" | 该写 WHY 没写 |

| 注释与代码一致 | 代码事实 | AI 编造不存在的行为描述 |

核对出差异 → 追加为新任务（T009…）→ 继续实现 → 再跑测试。

## 九、防跑偏设计原理（为什么这套能产出规范代码）

1. **类型化模板**：Controller/Listener/Job 各自的方案格式固定，AI 和人都知道"该写什么"，没有发挥空间 = 不会跑偏
2. **验收场景前置**：方案阶段就把"怎么算对"写死，第 4 步直接翻译成测试，偏差可检测
3. **约束硬规则**：第 2 步的约束是"能检查对错"的规则，AI 编码时逐条对照
4. **角色分离**：写测试的人/标准 ≠ 实现代码的 AI，防止"骗绿"（改断言、写假测试）
5. **收敛兜底**：实现完必须按类型逐条核对，防规格漂移
6. **人工最后把关**：测试绿 + 验收报告 + 抽查，三重确认后才上线
