# Spec Coding 具体步骤与中间产物详解

## 一、定义与核心思想

**Spec Coding（规格化编程）** = 先写规格，再让 AI 编码代理按规格实现。它由 GitHub 主导落地为开源工具 **Spec Kit**，方法论称为 **Spec-Driven Development（SDD）**。

三个关键转变：
- **"代码是真相之源" → "意图是真相之源"**：规格（spec）取代代码成为项目的最高真相，代码只是规格在某种语言/框架下的"表达"
- **规格从"文档"变成"可执行产物"**：不是写完就丢的脚手架，而是直接驱动实现的活物
- **人的角色从"作者"变成"舵手 + 验证者"**：AI 生成产物，人负责把关方向、发现缺口、纠正偏差

一句话概括流程：**Constitution（宪法）→ Specify（规格）→ Plan（计划）→ Tasks（任务）→ Implement（实现）→ Validate（验证）**，每个阶段产出 Markdown 产物，喂给下一阶段。

---

## 二、六步完整流程与中间产物

### 第 0 步：宪法（Constitution）

**做什么**：用 `/speckit.constitution` 建立项目的"不可违背原则"——架构基因。

**中间产物**：

| 产物 | 内容 |
|---|---|
| `memory/constitution.md` | 组织规范、测试要求（如"禁止无测试的代码"）、强制技术栈、复杂度上限（如"≤3 个项目"）、安全合规门禁 |

> 它相当于项目的"宪法"，后续所有 plan 都要过"宪法检查"（Constitution Check Gate），违规必须说明理由。

---

### 第 1 步：明确规格（Specify → PRD）

**做什么**：用 `/speckit.specify` 输入高层想法（**what 和 why，不谈技术**），AI 生成完整功能规格。自动创建特性分支 `specs/[001-feature-name]/`。

**中间产物**：`spec.md`（PRD），包含：
- **用户场景与测试**：按优先级 P1/P2/P3 划分的用户故事，每个故事有"独立测试方法"
- **边界用例（Edge Cases）**：强制补齐遗漏场景
- **功能需求**：编号 FR-001、FR-002…（"系统必须允许用户创建账户"）
- **关键实体（Key Entities）**：涉及数据的核心对象
- **成功标准（Success Criteria）**：可验证的验收条件

> 关键：这是**活的文档**，随理解加深持续演进，不是一次写完归档。

---

### 第 2 步：澄清（Clarify）— 进阶流程新增

**做什么**：在规格与计划之间插入一步，专门消除歧义、补齐依赖和边界用例，让 AI 把"没说清的地方"逐个盘问清楚。

**中间产物**：更新后的 `spec.md`（歧义已消除、依赖已列出、边界已补全）。

---

### 第 3 步：技术计划（Plan）

**做什么**：用 `/speckit.plan` 输入技术栈、架构、约束（how），AI 先生成调研，再产出设计文档。

**中间产物**（`/plan` 一次性生成 5 类）：

| 产物 | 内容 |
|---|---|
| `plan.md` | 技术上下文（语言/依赖/存储/测试/目标平台/性能目标/约束/规模）、项目结构、复杂度追踪表 |
| `research.md` | 选型调研：每个未知项 → 决策 + 理由 + 备选方案（如"WebSocket 库对比"） |
| `data-model.md` | 数据模型：实体、字段、关系、校验规则、状态流转 |
| `contracts/` | 接口契约：REST 端点、WebSocket 事件、CLI 命令模式 |
| `quickstart.md` | 快速验证指南：可运行的端到端验证场景、预期结果 |

> 此步有**宪法检查门禁**：设计前后各过一次，违反原则必须有正当理由。

---

### 第 4 步：任务拆解（Tasks）

**做什么**：用 `/speckit.tasks` 把 spec + plan 拆成可独立实现、独立测试的任务清单。

**中间产物**：`tasks.md`，格式为 `[ID] [P?] [故事] 描述`：
- **按用户故事分组**：Phase 1 Setup → Phase 2 基础（阻塞所有故事）→ 每个用户故事一个 Phase → 最后 Polish
- **`[P]` 标记并行**：无依赖任务可并行执行
- **测试任务先行**：先写测试、确认失败（FAIL），再写实现
- **含 Checkpoint**：每个用户故事完成后独立验证

> 示例对比：Vibe 会说"做个认证"，Spec 任务列表则是"创建校验邮箱格式的用户注册端点（tests/contract/test_auth.py + src/api/register.py）"。

---

### 第 5 步：实现（Implement）

**做什么**：用 `/speckit.implement` 让编码代理按 tasks.md 逐个执行，也可 `/speckit.taskstoissues` 转成 GitHub issues 跟踪。

**中间产物**：
- **代码**（严格按模板规定的创建顺序）
- **测试**：契约测试 → 集成测试 → e2e → 单元测试（**测试先行，宪法强制 TDD**）
- **每次提交**：每个任务/逻辑组独立 commit

> 与 Vibe 的差异：你审阅的是**聚焦的小改动**，而不是千行代码堆。

---

### 第 6 步：验证与收敛（Validate / Converge）

**做什么**：
1. **Validate**：对照 spec 的验收标准逐条核验产物
2. **Converge**：用 `/speckit.converge` 让 AI 评估"代码 vs spec/plan/tasks"的差距，把遗漏的剩余工作追加为新任务

**中间产物**：验证报告 + 更新后的 spec/plan/tasks（进入下一轮迭代）。

---

## 三、完整目录结构

```
memory/
└── constitution.md          # 项目宪法（不可违背原则）

specs/[001-feature-name]/    # 每个特性一个分支
├── spec.md                  # ← /specify 产出：PRD
├── plan.md                  # ← /plan 产出：技术计划
├── research.md              # ← /plan Phase 0：选型调研
├── data-model.md            # ← /plan Phase 1：数据模型
├── contracts/               # ← /plan Phase 1：接口契约
├── quickstart.md            # ← /plan Phase 1：验证指南
└── tasks.md                 # ← /tasks 产出：任务清单
```

## 四、为什么能控制质量（设计精髓）

1. **模板即提示词**：模板本身约束 LLM 输出，checklist 相当于"规格的单元测试"
2. **门禁机制**：每个阶段有明确 checkpoint，**验证通过才进入下一步**——不满足就不前进
3. **测试先行**：契约/集成/e2e/单元测试在实现前写好，AI 的任务是"让测试变绿"
4. **追踪闭环**：每个需求 → 技术决策 → 任务 → 代码可追溯（traceability）
5. **变更低成本**：改需求只需"改 spec → 重生成 plan → 让 AI 重做"，不用推翻重构

## 五、一句话对比 Vibe

| | Vibe Coding | Spec Coding |
|---|---|---|
| 起点 | 一句大白话提示词 | 宪法 + PRD + 技术计划 |
| 过程 | 对话式边聊边写 | 线性门禁式：规格→计划→任务→实现 |
| 产物 | 代码 | 规格、计划、数据模型、契约、任务清单、代码、测试 |
| 人的角色 | 鉴赏家（凭感觉验收） | 舵手 + 验证者（逐级把关） |
| 真相之源 | 代码 | 规格（意图） |
