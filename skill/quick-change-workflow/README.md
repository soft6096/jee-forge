# quick-change-workflow

小改动工作流（quick change）：在**已有模块上做小改动**（缺陷修复 / 优化 / 小需求补充）时的纪律——先判类型 → 复现与产物定位 → A/B/C 根因分层（证据，禁止盲试）→ 按层处理（A 改码；B 轻量修/补 3.x + 代码对齐；小需求 1.1 补项 + 3.x 补段；C 大变更转 0.8）→ 最小改动（全量注释/日志）→ 功能回归 → `/check-standards` 兜底 → 交付单 + 经验沉淀。

**动接口契约的交付口径**：只要改了 URL / 入参 / 出参 / 错误码 / 成功失败语义（A、B、短路三档都一样），交付必须按「改了什么 → 接口 → 入参 → 出参改前改后对照表 → 前端要做 → 测试要做」6 段给，缺段不算交付完成；B 档落交付单时填模板 5.3 节。

**核心动机**：简单单表 / 小改动不该被 1.1~5.3 完整流程拖慢、烧 token——识别为小增量即走本流程轻量处理；只有需要升版本目录 / 跨模块 / 重走主链的大迭代才转 ai-dev-workflow 0.8。

## 安装

随 jee-forge 家族一体安装（见仓库根 README）。也可单独使用本目录。

## 使用

```text
/quick-change <bug 描述 / 要补的小需求 / 优化点 或路径>   # 或自然语言"这个 bug 帮我修"/"在 XX 模块补个 XX"
```

## 边界

- 全新模块 / 无既有产物的完整新功能 → ai-dev-workflow 完整流程
- 真·零散新增一个独立接口（无既有模块产物需同步）→ ai-dev-workflow 轻量模式
- 需要升版本目录 / 跨模块 / 重走 1.1~5.3 主链的大迭代 → ai-dev-workflow 0.8 `/change-impact`
- 已有模块上的小增量（修 bug / 优化 / 补一个小功能点）→ 本流程（产物定位 + 轻量同步，产物同步不豁免）；模块无 `docs/` 产物时走「无产物基线」，**不踢出流程**
- 完成统一 `/check-standards` 兜底核对

## 目录

```text
quick-change-workflow/
├── SKILL.md                    # 入口 + 工作流 + 边界

```
