# 小改动工作流 quick change（缺陷修复 · 优化 · 小需求补充）

**定位**：已有模块上的**非全流程**通道。先确认期望在哪段产物、根因是什么，再动手；但**不为小改动铺 1.1~5.3 全套重流程**。

## 先判：要不要进场

**这四条是快出通道**（不铺下面的定位/分档/同步）：

| 情形 | 怎么做 |
|---|---|
| 用户已指明文件 / 方法 / 改法 | **短路**：直接改 → 改前复现、改后验证 → 四行交付 + 收尾动作（见下）；跳过 **A/B/C 分档**与产物定位（**"是否属小改动"的入场判定与判档行不省**） |
| 照样板、照某模块写新代码 | 参考样板直接写 → 注释/日志 → 兜底核对（即 ai-dev-workflow 轻量模式） |
| 纯日志排查（日志已指出位置） | 读日志定位 → 改 → 跑一次验证 |
| 临时试验 / 一次性脚本 | 直接写，不落产物、不落单 |

**进场信号**（命中任一）：说不清改哪 / 要查影响面 / 动接口·出参·字段·码值·口径 / 需留痕交付 / 同一问题已改 2 次未解。

**判档结论先落一行**（与 ai-dev-workflow 文首「入口分诊」同一口径）：回答第一句写「判档：小 → quick-change（依据：…）」。**档位或规模判不清 → 先问程序员**：一次列清「按小改动继续（本流程）」与「转 ai-dev-workflow 完整流程」两条路 + **【AI 推荐】** + 理由，等答复再动手；**禁止**"先按小改、不行再说"、**禁止**"先按大的跑反正不会错"——两种默认都是替用户拍板。

> 短路也受约束：保留"改前复现 → 改后验证"，注释与日志照旧；省掉的是 A/B/C 分档、产物定位、交付单（**"是否属小改动"的入场判定与判档行不省**）。**短路收尾**（一次给出，中途不打断）：**四行交付**——改了什么 / 根因 / 影响面（谁调用、会波及其它入口吗）/ 怎么验证的（影响面查法：搜方法名 / 接口 URL / 字段名，列调用点「文件:行号」，≤5 处）+ 下方的「收尾动作」。**四行不加长**；注释/文案/明显 typo 这类无外溢改动 → 只需四行（**`/check-standards` 兜底仍不豁免**）。
> **边界**：发现产物里没有这条期望 → 只提示"产物缺这条，要不要补"，不自行改产物；不写测试，除非该问题复发过或用户要求。

## 无产物模块（存量项目常态）

该模块 `docs/` 下没有 1.1 / 3.x 产物时 **不踢出流程**，走「无产物基线」：

- **定位降级**：以接口现状（URL / DTO / VO / 实现类）+ 用户描述代替 1.1 → 3.x.1 → 3.x.2
- **判档不变**：仍看"期望要不要变"，但判据改为「用户口述的期望 vs 现状代码」
- **交付口径**：注明「无产物基线，本次未做产物同步」；同类扫描命中的位置即后续补产物的线索；**不顺手建产物**（补 1.1/3.x 属完整流程，除用户要求）
- 纯新增零散接口（无任何既有产物需同步）→ ai-dev-workflow 轻量模式；完整新功能 → 1.1~5.3

## 分档（唯一判定表：增量类型 × 产物动不动）

bug 的本质是"期望已存在、代码没做到"，天然不动产物。**A/B/C 既是档也是根因层**（同一套判定，不再分两张表）：

| 增量类型 | 产物动不动 | 档 | 处理 | 交付 |
|---|---|---|---|---|
| 纯 bug / 口径不变的优化 | 产物（无产物时=现状代码）里查得到这条期望 → **不动** | **A 改码**：实现偏离产物 | 按产物改码，最小改动 | 1~2 文件单方法：对话一句话（改动点 + 根因 + 验证 + **同类扫描 N 处/无**）；多文件/公共方法：3~5 行记录，不套模板 |
| 小需求 / 口径小调整 / 优化改了验收场景 | 期望本身要变，或在已有功能项下补一段 → **动** | **B 产物同步**：产物要修/要补 | 先轻量改 3.x（小需求补 1.1 功能项）→ 再改码对齐 | 交付单 `docs/<模块>/quick-change-<时间戳>.md`（模板 `templates/quick-change-交付单.md`，含产物同步记录） |
| 升版本目录 / 跨模块 / 重走主链 | 全链同步 | **C 转出**：需求大变更 | 停，转 ai-dev-workflow 0.8 `/change-impact` | 停止原因 + 建议路径，不填交付单 |

- **判定要有据**：A/B 都要说清「产物哪一段（无产物则现状哪一处）vs 代码哪一处」，禁止无依据选档
- **bug 误判拦截（初判 → 定位后复核）**：产物里查不到这条期望（或与用户说的不一致）→ 不是纯 bug，**强制改判 B 或转出**，不按 A 裸改；"需求变了"常被当 bug 报
- **A 档不等于无纪律**：根因说明、全量注释、方法级日志、复现验证不豁免；豁免的只是**产物改动、产物定位章节与交付单**——"期望确实在产物里（或与现状一致）"这步只读查证仍要做

## 收尾动作（短路 / A / B 三档共用）

- **同类扫描（必做，各档统一）**：用 1~2 个关键标识（方法名/字段名/常量）搜同写法，**只列位置不动手**；只输出「文件:行号」，超过 5 处只报数。命中 >2 处 → **并入本次按 A 档正式处理**（一次改完，别留半改），而不是"升档重来"。注释/文案/明显 typo 这类无外溢改动 → 报「无同类」。
- **经验沉淀（条件触发）**：同一根因**第 2 次出现**才写 `docs/experience.md` 一行「现象 → 根因 → 改法」（跨模块通用标 `[HARD]`）；首次出现只在交付里说清根因，不落文件。写入前只读尾部 30 行。

## 交付：接口契约变更（跨端 6 段）

**触发**：本次改动动了**接口契约** —— URL / 路径 / 入参字段 / 出参字段 / 字段类型 / 错误码 / 成功失败语义（**含"原来报错、现在改返回空数据/空壳"这类语义变化**）。

**与档位无关**：A 档、B 档、短路**一律适用**；纯内部改动（不动上述任一项）仍按原口径（一句话 / 四行），不套 6 段。

**顺序固定，缺任一段不算交付完成**：

1. **改了什么** —— 一句话结论 + 只点受影响接口/模块
2. **接口** —— 方法 + 路径（代码块），并明写哪些相邻接口**没动**
3. **入参** —— JSON 示例 + 关键字段；未变也写"未变"
4. **出参** —— **"改前 → 改后"对照表**，逐行覆盖成功 / 各错误码 / 边界（语义变化单独一行）；**禁止用描述性段落代替对照表**
5. **前端要做** —— 编号动作项（判空 / 传参 / 错误分支 / 文案），没有则写"无"
6. **测试要做** —— 编号可执行用例（正常 / 边界 / 权限 / 回归），没有则写"无"

**硬要求**：

- 只列**受影响**接口，不铺全量；不写复盘长文与排查心路
- 第 5、6 段必须是**可直接照做**的动作与用例，禁止写"注意兼容""关注一下影响"这类空话
- B 档落交付单时，同一套内容填进模板「5.3 接口变更与跨端待办」；正文只维护一处（对话给结论，单据按栏目留痕）

## 交互闸门（只有这 5 处开口，其余自决）

正常情况：A 档从一句话到交付 **0 次确认**，B 档 1 次（产物改哪段）。

| # | 必须问（示例） |
|---|---|
| 1 | 判档不清（修实现，还是口径也变了）——“这是修实现，还是要改口径？” |
| 2 | 产品口径型（权限/可见性/默认值/保存下载规则）——“期望口径是 A 还是 B？” |
| 3 | B 档要动产物——“3.1 验收场景加一条，可以吗？” |
| 4 | 兜底有项未到位——“这两处注释缺失，现在补？” |
| 5 | 同一问题改 3 次仍不过——“已试 3 种改法，转完整流程？” |
| 6 | **档位/规模判不清**（小改动 vs 需升版本/跨模块）——“按小改动继续，还是转 ai-dev-workflow 完整流程？”（给两条路 + 【AI 推荐】） |

> 开口即按全局规则（global-rules.md）给裁决推荐：`- **【AI 推荐】** —— 理由：…（什么情况下改选别的）`，推荐项放第一位、不加勾选框；**禁止只把选项抛给用户**。

**禁止开口**：能否开始改 / 逐步报进度 / 要不要落交付单 / 要不要跑 check-standards。

## 执行步骤

```
0 前置：记录用户原话 → 确认项目模式 + 该模块 docs/ 产物
1 初判档：增量类型 × 产物动不动 → A / B / C（定位后复核，可改判）
2 产品口径型 → 先对齐期望；新的大口径 → 转出
3 产物定位（只读，A 档也做）：1.1 → 3.<n>.1（核心逻辑/验收场景）→ 3.<n>.2（入参/出参/错误码）
  用产物当地图别翻代码猜；小需求 = 定挂载功能项与要补的段；无产物 → 「无产物模块」降级
4 改：A 按产物直接改码；B 先轻量修/补 3.x 对应段 → 再改码对齐
5 验证：相关功能回归 + 受影响验收场景抽查，留证据（无法复现 → 替代证据 + 标注）
6 收尾：同类扫描 → /check-standards 兜底 → 按档交付 → 经验按条件沉淀（同根因第 2 次才写）
```

## 与家族其它 skill 的边界

| skill | 边界 |
|---|---|
| ai-dev-workflow 0.8 | 大迭代（升版本目录/跨模块/重走主链）→ /change-impact 定位旧产物 + 变更映射，人确认后再同步 |
| ai-dev-workflow 轻量模式 | 无既有产物需同步的零散新接口、照样板写码 |
| ai-dev-workflow 完整流程 | 全新模块 / 完整新功能 → 1.1~5.3 |
| check-standards | 改动完成后兜底核对（注释/日志/规范逐项，附证据） |
| java-code-standards / comment-standards / database-standards | 按对应规范写码（命名/分层/注入/日志/事务/注释；涉 SQL/表/字段 → database） |

## 轻量产物同步规则（仅 B 档，不走 0.8 整套）

- 只改本次涉及的 3.x 段落（核心逻辑/验收场景/接口清单对应行），不做无关产物重构；小需求在 1.1 补功能项（含 GIVEN-WHEN-THEN）
- 先改/补产物对应段 → 再改码对齐，**产物为源**；逐条登记交付单「产物同步记录」（旧表述 → 新表述 + 原因 + 联动文件）
- 检查引用被改段落的其它产物（1.1 依赖关系、4.1 任务）；**不新建版本目录、不重跑 5.3**
- A 档禁止为"显得规范"改正确产物；大变更禁止当小改动在本流程改口径

## 硬性要求

- 先记录用户原话再转工程问题（禁止一开始就改写）；根因不清禁止改码
- 最小改动：只改根因相关，禁止"顺手优化"/重构/无关清理
- 注释与日志不豁免：本次修改/新增代码全量注释 + 方法级日志

## 完成标准（按档勾选）

**共同**：进场已定（或短路）+ **判档行已写**（判不清已问用户并按其选择执行）· 原话已留 + 产品口径已对齐 · 根因清楚（产物哪段/现状哪处 vs 代码哪处）· 最小改动且本次代码全量注释 + 方法级日志 · 功能回归证据（改前复现/改后通过；**无法复现时**用日志/调用链/单测/线上验证替代并显式标注「未复现，依据 X 推断」，**禁止直接跳过验证**）· **同类扫描已做（列位置或报「无同类」；>2 处已并入本次处理）** · 经验沉淀按条件（同根因第 2 次出现才写）· **动了接口契约 → 跨端 6 段齐全**（改了什么/接口/入参/出参对照表/前端要做/测试要做；见「交付：接口契约变更」）· `/check-standards` 兜底（脚本扫描零 API 成本，但 manual/warn 项仍需逐项判定并附证据；不因改动小跳过）

**短路**：复现/验证各跑一次（贴结果）· 四行交付（含影响面查法结论）· 收尾动作已做（同类扫描 / 条件沉淀）· 兜底同共同项

**A 档**：产物未动 · 交付含「同类扫描 N 处/无」· 不落交付单、不写定位章节 · 无产物模块已标注基线

**B 档**：定位完成（无产物已降级）· 3.x 对应段已轻量修正（小需求：1.1 补项 + 3.x 补段）+ 产物同步记录 · 代码与产物对齐 · 交付单已落盘

**C 转出**：已转 0.8，未在本流程硬做；不落交付单，只给停止原因 + 建议路径

经验按需写入 `docs/experience.md`。
