# 小改动 quick change · 执行细则

> **判定口径不在这里维护**：要不要进场、分档（A/B/C）、交互闸门、交付与完成标准统一见 `SKILL.md`。
> 本文件只写**执行顺序与每步动作**，避免两份判定表各自漂移。

## 输入

- 增量请求：用户原话 / 复现入口（URL、接口、页面、参数）/ 期望 vs 实际 / 报错日志；或要补的小需求点 / 优化点
- 项目现状：老项目先有 `docs/0.5-存量代码扫描.md`（无 → 按 ai-dev-workflow `/legacy-scan` 补）；`ls docs/` 确认该模块是否有历史产物

## 执行（编号对应 SKILL.md「执行步骤」）

**0 前置：记录原话 + 项目模式确认**
- **完整保留用户原话**（先记录再转工程问题，禁止一开始就改写用户问题）
- 确认项目模式与模块产物目录（`ls docs/`，有产物 → 本次定位/同步都以它为基准）

**0.1 进场判断**
按 SKILL.md「先判：要不要进场」：
- 命中**短路**（用户已指明文件/方法/改法）→ 直接改 → 改前复现、改后验证 → 四行交付 + SKILL.md「收尾动作」（同类扫描必做 / 经验沉淀条件触发）→ **结束，不进入下面各步**
- 命中照样板写码 / 纯日志排查 / 临时试验 → 不进本流程，按对应做法直接做
- 命中进场信号 → 进 1

**1 初判档（定位后必须复核）**
按 SKILL.md「分档」表落 A / B / C，并写下判定依据（产物哪一段 / 现状哪一处 vs 代码哪一处）。判不清 → 闸门 #1 问一句。

**2 产品口径型？**
问题涉及按钮/页面/文案呈现、角色权限/可见性、默认值/边界状态、生成/保存/下载规则等"该是什么样"的口径 → 先与用户对齐期望（按闸门 #2，带【AI 推荐】）：
- 新的**大口径**（与现有口径/冻结合同不符）→ **C 转出**，停
- 一个点的小口径补充/调整 → 按 B 处理
- 纯技术错误（报错/接口失败/样式/计算错误）→ 继续

**3 产物定位（只读，A 档也做）**
- 缺陷/优化：1.1 功能清单对应功能项 → `3.<n>.1-<功能>-技术方案.md`（核心逻辑/验收场景）→ `3.<n>.2-<功能>-接口清单.md`（入参/出参/错误码）
- 小需求补充：确定该功能点挂进哪个功能项（或需新增功能项），定位要补的 3.<n>.1 方案段 / 3.<n>.2 接口字段
- **无产物** → 按 SKILL.md「无产物模块（存量项目常态）」降级为无产物基线，不踢出流程
- **复核判档**：产物里查不到这条期望、或与用户说法不一致 → 改判 B 或 C，**不要顺着改代码**

**3.1 定位对照（按现象查表，别翻代码猜）**

| 问题/增量信号 | 先看产物 | 重点看 |
|---|---|---|
| 接口 URL 调不通 / 404/405 | 3.<n>.2 接口清单 | 路径/方法/参数是否与实现一致 |
| 入参报错 / 校验不对 | 3.<n>.2 + Controller 方案 | 参数定义、校验规则、DTO 结构 |
| 出参字段不对 / 缺字段 | 3.<n>.2 + 3.<n>.1 逻辑 | VO 结构、组装逻辑、是否该返回 |
| 状态/计算结果不对 | 3.<n>.1 技术方案 | 核心逻辑、验收场景预期 |
| 边界/异常场景炸 | 3.<n>.1 技术方案 | 验收场景三态（合法/非法/边界）是否缺漏 |
| 补个小功能点/加字段 | 1.1 功能清单 + 目标 3.<n>.1/.2 | 挂进哪个功能项、需补的验收场景/接口字段 |

**4 按档处理**
- **A**：按产物直接修正代码（最小改动），产物不动
- **B**：① 轻量修/补产物（规则见 SKILL.md「轻量产物同步规则」，逐条记入交付单「产物同步记录」）→ ② 改代码与修正后产物一致（产物为源）→ ③ 检查引用被改段落的其它产物（1.1/4.1/其它 3.x）受影响则同步标注
- **C**：输出「停止原因 + 建议变更路径（ai-dev-workflow 0.8 /change-impact）」，结束；**不进入修复、不写产物伪记录**

**4.1 写码约束**
- 只改根因/增量相关，禁止顺手优化/重构/无关清理
- 本次新增/修改代码全量注释（comment-standards）+ 方法级日志（java-code-standards §1.6）；涉 SQL/建表/加字段 → database-standards

**5 验证（功能回归）**
- 相关功能回归 + 受影响验收场景抽查（B = 修正后场景；小需求 = 新功能项验收场景）
- 证据：运行日志 / 关键文件:行号 / 接口实测（需运行时行为验证可显式用 `test-workflow`（`/gen-test`））
- **无法复现时**（线上数据 / 第三方回调 / 无环境）：用日志、调用链、单测或线上验证替代，交付里显式标注「未复现，依据 X 推断」；**禁止直接跳过验证**

**6 兜底与交付**
- 加载 **check-standards** 对本次改动核对（逐项附证据），未到位项按闸门 #4 问是否补齐
- 交付介质见 SKILL.md「分档」表的交付列：A 档不落单（对话一句话 / 3~5 行记录）；B 档落 `docs/<模块>/quick-change-<YYYYMMDDHHMMSS>.md`（模板 `templates/quick-change-交付单.md`）
- 坑记入 `docs/experience.md`（**条件触发**：同一根因第 2 次出现才写，规则见 SKILL.md「收尾动作」；跨模块通用 → 标 `[HARD]`，人工走家族固化流程）

## 输出（按档）

- **A 档**：代码改动（最小）+ 复现/修复证据 + 一句话交付（改动点 / 根因 / 验证）
- **B 档**：交付单 + 代码改动（最小）+ 功能回归证据 + 产物同步记录
- **C 转出**：停止原因 + 建议变更路径（不落单）

## 完成标准

与 SKILL.md「完成标准（按档勾选）」同一套（共同 / 短路 / A 档 / B 档 / 转出），不在本文件重复维护。
