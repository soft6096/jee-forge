# 经验回流指南（使用者 → jee-forge 维护者）

> 面向下载使用 jee-forge 的团队：你们项目里积累的坑/使用总结，如何交回维护者，让"所有使用者"都受益。

## 一、经验放哪、归谁

| 级 | 位置 | 归谁 | 会不会"重复" |
|---|---|---|---|
| 任务级 | 验收报告「本次经验」节 | 使用者本人 | 不与技能重复 |
| 项目级 | 使用者项目 `docs/experience.md` | 使用者自己的项目 | 不与技能重复 |
| 家族级 | 维护者把经验**翻译成规则**写入 jee-forge（规范条目 / check-standards 核对项） | 评审后全体共享 | 是"规则"不是"经验文件"，语义由条目状态管理，不产生文件重复 |

> 注意：**不把** experience.md 原样复制进 jee-forge；只把其中的通用教训固化成"规则"。

## 二、使用者怎么记（条目格式）

1. 在项目 `docs/experience.md` 按模板（`skill/ai-dev-workflow/templates/通用-经验记录.md`）记一条；
2. 给每条打状态：`本地`（仅本项目）/ `待上缴 [HARD]`（跨项目通用，准备交回）；
3. 填"建议固化目标"：想让它最终进哪个域——check-standards / java-code-standards / comment-standards / database-standards / build-standards / test-standards / ai-dev-workflow（流程/模板/命令）/ 仅项目本地。

## 三、怎么交回（任选）

- GitHub **Issue**（附 `docs/experience.md` 内容，建议标上缴头）；
- GitHub **Discussion**；
- 或维护者约定的其它渠道（邮件等），随仓库最新说明为准。

> 交回时连同文件顶部的「上缴头」（来源/联系/授权声明），方便维护者归集与回信。

## 四、维护者收到后（作者侧 SOP）

1. **评审**：是否通用、是否带证据、是否符合 jee-forge 的技术栈边界；
2. **按"建议固化目标"分拣**到对应 skill：
   - 核对类 → check-standards 新增/修订核对项（顺延编号并记录）
   - 代码/注释/SQL/构建/测试类 → 对应 standards 技能的自检清单或规范段落
   - 流程/模板类 → ai-dev-workflow 的命令/模板/SKILL 约定
   - 仅项目本地 → 不接收，说明原因
3. 接受/拒绝都要回信：接受 → 回填"已固化 → <具体出处>"；拒绝 → 说明理由（太个性 / 证据不足 / 越界）；
4. **发布**新版本后通知提交者 `git pull`，提交者把对应条目标记 `✅ 已固化 → X` 并移入归档。

## 五、维护者定期征集（作者侧约定）

- 每个版本周期末（或约定频次），在 Issue/Discussion 发起"经验征集"，请使用者发来各自的 `docs/experience.md`；
- 已固化的历史条目使用者会自行归档，征集到的都是"新存活条目"，天然去重。

## 六、接受 / 拒绝标准

| 接受 | 拒绝 |
|---|---|
| 跨项目通用、带真实案例/证据、可写成可检查规则 | 仅某项目私有约定 |
| 与现有规范/核对项不冲突或可修订融合 | 证据不足、表述模糊无法固化成"能检查对错"的规则 |
| 在 jee-forge 技术栈边界内（Java/Spring 系） | 超出家族边界（可建议单独 skill 或别家工具） |
